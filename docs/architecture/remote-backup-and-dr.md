# 远端备份、异地容灾与分布式部署（研讨中）

> 状态：**研讨中**。§2 是已实现的现状，其余是分阶段的问题梳理与倾向性建议，尚未定案。
>
> 触发它的是[统一动作 ABI](action-abi.md) §8——批量数据只走「动作自己打开目的地」一条路径，
> 而今天「目的地」只能是本地文件系统路径。要让备份离开这台机器，先要回答目的地还能是什么。

## 1. 三个目标不是同一个问题

把它们分开是本文最重要的一件事。混在一起谈会得到一个既做不好备份、也做不成分布式的设计。

| 阶段 | 目标 | 成功的标准 |
| --- | --- | --- |
| **一、远端备份** | 备份落到另一台机器 | 源机器整个烧掉，数据还在 |
| **二、异地容灾** | 另一台机器能**接管** | 源机器烧掉后，远端能把服务跑起来 |
| **三、分布式部署** | 多台机器**同时**承载不同 Module | 一台机器承载不下的部署可以横向铺开 |

阶段一只需要传输与信任；阶段二还需要远端具备运行能力与一次可控的接管；**阶段三则要改动 Core
的基本假设**——今天的 Contract、Resource、Capability 解析全部假设「一个部署 = 一台宿主」。

一和二是同一条路上的两站，三是另一条路。本文详述一，勾勒二，为三划边界。

## 2. 现状：目的地只能是本地路径

`internal/runner/backup.go` 有三种传输模式，**目的地全是本地文件系统路径**，没有任何网络传输
代码：

| 模式 | 做法 | 目标要求 |
| --- | --- | --- |
| `send` | `btrfs send \| btrfs receive` | 目标必须是 btrfs |
| `send-file` | `btrfs send` 写成流文件 | 任意文件系统 |
| `copy` | `rsync -aHAX --numeric-ids` | 任意文件系统 |

用户今天能做的「远端备份」，实际是**自己挂一个远端目录再往里写**（外接盘、NFS/SMB、
rclone/s3fs 挂载点）。代价是这些挂载 ANAS 看不见也管不了：挂载掉了，备份会静默写到本地盘上；
而且 `send` 模式要求 btrfs，挂载来的 NFS 与对象存储都不满足，只能退到 `copy` 或 `send-file`，
增量的价值随之丢失。

### 2.1 一个已经就位的关键资产：目的地只有一种形状

无论哪种模式，目的地的结构完全相同：

```text
<dest>/<backup-id>/
  backup.yml     manifest；complete: true 最后写
  snapshot.yml   源快照自身的元数据
  meta/          config.yml、config.lock.yml、secrets.yml、deployment-state.yml
  deployment/    部署制品的完整副本
  data/          业务数据（子卷或普通目录）
  data.stream    ……或 send-file 模式下的 btrfs send 流
```

这条不变量是远端化能够只改一层的原因：**「远端」是传输问题，不是格式问题。** 恢复路径不需要
知道数据是从本地盘还是从另一台机器来的。

## 3. 阶段一：远端接收

### 3.1 对端是什么

两种，不互斥：

| 对端 | 说明 | 代价 |
| --- | --- | --- |
| **完整 ANAS** | 两台 ANAS 互为备份目的地 | 对端要装完整 ANAS；但阶段二天然可达 |
| **接收端 CLI** | 远端只装 `anas` 二进制，只承担接收 | 门槛低（一台 VPS、一台旧机器就行）；但它只是个仓库，接管不了 |

倾向：**两者用同一套协议**，差别只在对端愿意暴露哪些动作。接收端 CLI = 只开放接收相关动作的
ANAS。这样不必维护两套实现，也不必在阶段二时换协议。

### 3.2 传输：SSH 还是原生 mTLS

| | SSH | 原生 mTLS |
| --- | --- | --- |
| 现成程度 | `btrfs send \| ssh host btrfs receive` 是这套工具链最经典的用法 | 需要自己定协议 |
| 凭据 | SSH key：归谁、怎么轮换、要不要限定 `command=` | 与 `compute` 契约同构：固定服务端证书 + 受限客户端证书 |
| 对端要求 | 对端要有 sshd 与一个可登录账号 | 对端只需跑 ANAS 的监听端 |
| 权限收敛 | 靠 `authorized_keys` 的 `command=` 限死，写错就是完整 shell | 协议本身只有具名动作，没有「万一写错就是 shell」这种失败模式 |

倾向：**原生 mTLS**，理由是最后一行。`compute` 那套已经验证过这个形状——固定服务端证书、
每消费者一张受限客户端证书、动作具名且参数类型化。SSH 的 `command=` 限制是一条容易写错、
写错就完全失效的配置，而 mTLS + 具名动作没有等价的「一不小心就开成 shell」的可能。

SSH 可以作为**过渡路径**保留：它今天就能用，只是要在文档里写明它的权限收敛全靠运维配对。

### 3.3 方向：拉，不是推

这条对**勒索软件抵抗**是决定性的。

- **推（源 → 远端）**：源机器持有能写远端的凭据。源机器被攻陷 ⇒ 攻击者能删掉远端的备份。
  备份和生产同时没了。
- **拉（远端 → 源）**：远端持有能读源的凭据，源机器**不持有任何能改远端的东西**。源机器被攻陷，
  远端的历史备份仍然完好。

倾向：**默认拉模型**。源端只开放「读快照 / 发送流」这类动作，且**没有任何删除远端数据的动作**。

推模型仍应支持（它在网络拓扑上更简单，源在 NAT 后面时可能是唯一选择），但必须在文档里点名它的
代价，并且配合远端的**只追加保留策略**——远端自己决定保留多久，不接受源端的删除指令。

### 3.4 增量：对端必须共享「有哪些快照」的视图

`btrfs send -p <parent>` 的前提是**接收端已经有那个 parent**。所以协议里必须有一步「问对端有
哪些 backup-id / snapshot」，据此选出共同祖先再发增量。

这也是**只有 btrfs 对端才能真正增量**的原因：对象存储没有子卷语义，`send -p` 的流只能整块当
不透明对象存着，恢复要先拉全量。因此：

- **btrfs 对端**：真增量，第二次备份只传变化部分——这是相对 `rsync` 的核心优势；
- **非 btrfs 对端**（对象存储、NFS）：只能 `send-file` 全量或 `copy`。可用，但别把它当增量方案。

## 4. 横切问题

### 4.1 secrets 在备份里，所以远端和生产一样敏感

`meta/secrets.yml` 是备份的一部分——没有它恢复出来的部署起不来。直接后果是：**放备份的那台机器，
安全等级等同于生产机器。** 一台随手找的旧机器或便宜 VPS 不满足这个要求。

三条候选路径，都要定案后才能实现：

1. **静态加密，密钥由运维持有**：远端只存密文，远端被攻陷不等于 secrets 泄漏。代价是恢复时必须
   有人提供密钥——与「异地容灾要能自动接管」直接冲突。
2. **分离复制**：`data/` 自由复制，`secrets.yml` 单独走一次显式的、有人参与的流程。安全，但让
   「一键容灾」不成立。
3. **对端同等信任**：最简单，也最危险。只在对端确实由同一个人以同等标准运维时可接受。

倾向：**默认 1，允许显式降级到 3**，并在文档里把 3 的含义写成一句话：「你在这台机器上放的是
生产系统的全部钥匙」。

### 4.2 特权

`btrfs receive` 与 `btrfs send` 都需要 `CAP_SYS_ADMIN`（见[特权操作与 helper](privilege-helper-draft.md)
§1）。按[宿主特权动作通道](host-action-channel.md) §3.1 的划分，这两条归 `anas-hostd`。

因此远端接收端**也需要 `anas-hostd`**，也就是也需要那一次安装期 root。「只装个 CLI 就能收备份」
这个说法要打折扣：能收 `copy` / `send-file`，但要收 `send` 流成为子卷，对端必须完成宿主供给。

### 4.3 长时传输

跨机传输天然是长任务，且天然会断连。这正好落在[统一动作 ABI](action-abi.md) 已经定下的模型上：
job 在服务端跑到底、事件日志带序号可重放、断线重连续订、取消是协作式的。**远端备份不需要另造
一套进度与断连语义**，用现成的即可。

## 5. 阶段二：异地容灾

比阶段一多的不是数据，是**接管能力**：

1. **远端要能真的跑起来**：Module 镜像、Compose、Traefik 与证书、以及宿主级前置（Docker、
   可能的 Incus）。冷备份 + 一台什么都没装的机器 ≠ 容灾。
2. **域名与证书**：服务恢复后用哪个域名对外？切 DNS 还是接管同一个？`lego` 的账号与证书在
   `data/lego/` 里，能随备份过去，但 DNS 控制权不在备份范围内。
3. **一次可控的接管，而不是自动切换**：自动切换需要仲裁，仲裁需要第三方，否则**脑裂**——两边
   都认为自己是主，两边都在写数据，之后无法合并。倾向：**接管是一个显式的、破坏性的动作**，
   走[统一动作 ABI](action-abi.md) §9 的两段确认，人看着确认。
4. **回切**：接管之后原站修好了，数据怎么回来？这条常被忽略，但它决定容灾是不是一次性的。

## 6. 阶段三：分布式部署的边界

**这不是备份的延伸，是 Core 模型的改动。** 今天的假设是「一个部署 = 一台宿主」，多处依赖它：

- Contract / Resource 解析产出的是一台机器上的依赖顺序；
- Capability 绑定通过同机的 Docker 网络与环境变量投影完成；
- `HOST_*` 全局事实、macvlan 计划、Traefik 路由都以单宿主为前提；
- 部署事务与回滚是单机的，跨机就要面对分布式事务。

要做的话，第一个必须回答的问题不是「怎么把 Module 放到别的机器上」，而是
**「跨机的 Contract binding 是什么」**——`relational_database` 的 provider 在另一台机器上时，
连接信息怎么投影、凭据怎么传、故障时谁负责。在那之前，不要把阶段三的需求塞进阶段一的设计里。

阶段一与阶段二**不应当为阶段三预留接口**。为一个尚未定义的模型预留，得到的通常是既约束了当下、
又不匹配将来的接口。

## 7. 待决

- 传输协议定案：原生 mTLS 还是先上 SSH 过渡（§3.2）；
- secrets 的三条路径选哪条作为默认（§4.1）；
- 拉模型下源端需要开放的最小动作集；
- 远端保留策略由谁决定（倾向远端自己，源端无权删）；
- 非 btrfs 对端是否值得支持增量，还是明确只做全量（§3.4）。
