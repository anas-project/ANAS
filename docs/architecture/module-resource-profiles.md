# Module 资源运行方式设计

**状态：下一版本提案，尚未实施。** 本文解释如何用一条公共路径，根据内存等资源推荐、选择和应用
Module 配置组合。覆盖 `MODRES-R-001`—`MODRES-R-028`，规范来源为
[需求矩阵](https://github.com/anas-project/ANAS/blob/master/dev-docs/requirements/module-resource-profiles.md)，
里程碑及未执行的验收项目见 [实施计划](https://github.com/anas-project/ANAS/blob/master/dev-docs/plans/module-resource-profiles.md)。
本文不定义当前可执行命令或已经存在的 schema 字段。

## 1. 目标与非目标

Immich 提出了低内存、完整本地处理等需求，但处理方法应对全部 Module 一致。
一个“资源运行方式”是模块声明的一组有效配置、功能影响和资源证据；并非每个模块都必须有三档，
也不意味着“低于某个内存数字就自动改用另一种运行引擎”。

本版 [Immich 接入](/architecture/immich-module-design) 不依赖这个框架。
下一版本先提供**只读推荐、显式选择、受管应用**；不新增常驻资源调度器，不按空闲内存持续重启服务，
不自动购买资源、迁移数据库或把照片发送给未授权的远程 ML。

## 2. 复用边界

| 现有机制 | 在本方案中的用途 |
| --- | --- |
| Module inventory | 派生全部模块覆盖清单，避免手写名单遗漏新模块 |
| manifest/config 类型与默认值 | 校验模块声明和有效配置，保护用户显式设置 |
| 可选服务及条件 capability | 使配置决定真实服务集合和依赖，而非新增一套选择器 |
| 现有 plan 与共享应用层 | 一次计算供 CLI/Web 展示，不各写一套推荐逻辑 |
| 锁、deployment、配置变更分类 | 冻结选择，管理重启、冲突、失败补偿和回滚 |
| runtime 观察与问题记录 | 报告观测、限制未生效与 OOM，而非建立第二个健康状态库 |
| 临时存储与备份生命周期 | 保持数据安全；资源方式不绕过原有清理和恢复规则 |

只增加当前边界缺少的可选声明和规划逻辑。不得在 Core 中按 `immich`、`postgres` 等名称实现特殊策略。
模块自行描述经过验证的组合，公共逻辑只认识资源、配置和依赖语义。

## 3. 声明内容与兼容

声明需要表达稳定的方式标识、可配置项及默认值、保留/关闭的功能、必要能力、资源建议和证据来源。
这些是设计语义，不是已经存在的 manifest 键；实现前由 M0 对齐现有 schema 和向后兼容规则。

没有新声明的旧模块继续使用原有默认行为。需要纳入覆盖清单，但不能自动填一个未经测试的内存数字。
只有默认方式的模块也是正常情况；高资源业务未必存在安全的低内存等价物。
方式中的配置只用于补默认值，用户显式值优先；冲突时计划必须说明最终结果，而非私自覆盖用户配置。

不允许把 Secret 明文、数据目录迁移或放宽权限装进配置组合，绕过原有参数与变更授权。
共享 Provider 方式变化需要校验其全部已绑定 Consumer 的必要能力，不能只顾一个新应用。

## 4. 一次规划的数据流

```text
Module inventory + 已有配置 + 目标资源证据 + 管理员预算
                    │
                    ▼
        公共只读规划：方式候选、功能差异、预算和未知项
                    │ 管理员显式选择
                    ▼
        原有配置合并 → 条件依赖解析 → plan / lock
                    │ 应用前复核目标与硬约束
                    ▼
        原有 apply → 冻结 deployment → 现有生命周期
                    │
                    └── 原有状态观察 / 回滚 / 问题记录
```

配置组合必须在依赖解析前形成有效配置，之后通过原来的可选服务与依赖路径，避免推荐结果与真实服务集合不同。
解析后的选择与输入证据进入同一份冻结记录，CLI 和控制台只消费投影，不维护第二份配置真相。
下次重启加载冻结选择，不重新采样空闲内存后换档。

plan 保持只读。apply 重新检查目标身份、配置是否改变以及必要的硬约束；不足时拒绝原计划并给出原因，
不是在执行中无声改用更低功能组合。观测失效与硬约束失败要分别展示，不能把瞬时空闲减少当作永久不支持。

## 5. 资源预算模型

不同数字回答不同问题，不能压成单个 `memory`：

| 信息 | 含义 |
| --- | --- |
| 宿主容量 | 实际执行目标的物理/虚拟可用容量，不是操作端电脑的内存 |
| 有效限制 | VM、容器或服务的上限；未知或无法强制时明确标记 |
| 管理员预算 | 为系统、其他工作区、非纳管服务及当前工作区保留的额度 |
| 运行观测 | 某个时间点的使用与可用量，带目标和采集时间 |
| 测试证据 | 特定版本、平台、图库/任务规模和并发下的稳态与峰值 |

有效预算不超过已知的执行边界，并扣除保留量。未知目标不使用操作端数据代替，也不按无限资源推荐。
swap 单独展示，不计为等量 RAM；堆上限、容器上限与全进程实际占用也分别处理。

按实例身份计算共享开销。例如两个应用共享同一 PG，基础进程/缓冲开销计一次，应用增量分别计算；
两个独立 PG 实例不能仅因模块名称相同而去重。系统与控制面始终保留空间。
初次导入、索引构建、模型加载、视频处理、升级和备份的峰值需要考虑重叠；未经约束不得自行假定串行。

建议值分为实测、估算、未知。不给所有 Module 硬套同一阈值，也不因为 4GB 单容器能启动就承诺 4GB 整机全栈稳定。
实例数量、共享关系或版本改变时，旧的推荐证据需要重新评估。

## 6. 应用、回滚与安全

所有方式变更进入现有配置变更分类；需要重启时由原有生命周期处理。
失败保留已写入的事务证据与原配置，不能为凑预算删除原图、身份或数据库。
回滚恢复历史 deployment 的配置选择，再校验它当前是否可运行；不能重新推荐后把另一个组合当作原样回滚。

减少并发或关闭可选功能不影响 TLS、认证、Secret、网络隔离、管理员权限或撤权边界。
限制无法在目标 runtime 生效时，展示未生效或阻塞，不把声明值当作已执行的限额。
资源方式不增加独立的临时目录清理、备份任务或生命周期补偿状态机。

远程 ML 等方式只是有明确前提的候选：要有显式 endpoint、可信网络、版本匹配和数据流向授权。
低内存本身不是把用户数据发送出去的授权，远端失败也不能回退到公共服务。

## 7. 全模块实施与 Immich 示例

从现有 inventory 生成覆盖视图，逐模块记录：默认行为、多方式适用性、配置投影、共享依赖、功能影响和测试状态。
未提供多方式不代表未覆盖；未完成业务测试却宣称可用才是问题。
先验证高负载应用、共享数据库、轻量服务及可选服务等不同类型，再覆盖全部模块；新增模块触发证据检查。

Immich 的下一版本候选可以包括“本地 ML 关闭”“完整本地处理”，以及满足授权和连接条件后的“远程 ML”。
它们只是模块声明的示例，不是本版新增配置或全局固定档位；必要的上传、缩略图和媒体处理不能被误关。
Redis 仍专属、数据库仍共享、登录仍 OIDC-only，不随内存方式改变这些所有权和身份决策。

4GB、8GB 和受 cgroup/VM 限制的较大宿主用于容量实验，结论绑定具体版本、依赖组合与负载。
首批导入、持续上传、重任务和备份重叠都要测；用健康检查通过代替业务和数据完整性验收不成立。
未执行项目在 [计划](https://github.com/anas-project/ANAS/blob/master/dev-docs/plans/module-resource-profiles.md) 中保持未开始，
文档校验通过不能使这些运行能力提前变成已实施。
