# 日志与可观测性（研讨中）

> 状态：**研讨中，尚无结论**。本文只负责把问题问清楚、把已经散落在别处的既成事实收拢，
> 不给答案。有结论之后再改成设计文档。
>
> 触发它的是[统一动作 ABI](action-abi.md)：那份设计引入了 job 的**事件日志**，而 ANAS 里已经
> 存在若干种「日志」。在弄清它们的关系之前，事件日志的持久化位置与保留期定不下来。

## 1. 现在有几种「日志」

它们的读者、生命周期和敏感度都不一样，混为一谈会同时得到「查不到想查的」和「泄漏不该泄漏的」。

| 种类 | 内容 | 读者 | 现状 |
| --- | --- | --- | --- |
| **容器日志** | Module 容器的 stdout/stderr | 管理员排障 | Docker 自己管，ANAS 不接管 |
| **CLI 输出** | `anas apply` 等命令的人类输出与 `--json` 信封 | 执行命令的人 | 已实现，不持久化 |
| **job 事件日志** | 一次动作调用的 progress / warning / result，带序号可重放 | 控制台与 CLI 实时订阅 + 事后回看 | [统一动作 ABI](action-abi.md) §5，未实现 |
| **特权动作审计** | 谁在什么时候经 `anas-hostd` 执行了什么 | 事后追责 | [宿主特权动作通道](host-action-channel.md) §3.3 定为写 journal，未实现 |
| **部署与配置历史** | deployment、lock、resource state 的演进 | 回滚与排查 | 已实现，落在 `.anas/` 下 |

## 2. 待研讨的问题

### 2.1 事件日志与审计日志是同一份吗

两者内容高度重叠（都是「谁执行了什么、结果如何」），但要求相反：

- 事件日志要**详细、可重放、可截断**，服务于「现在这个任务跑到哪了」；
- 审计日志要**精简、不可篡改、长期保留**，服务于「三个月前那次删除是谁做的」。

合成一份会让保留期无解：按审计的要求留三个月，磁盘上就堆着三个月的进度条；按事件的要求几天
就清，审计就没了。分成两份则要回答它们怎么关联。

### 2.2 保留期与清理

- job 终态之后留多久？按条数、按时间，还是按总字节？
- 谁来清理——常驻进程、下次 invoke 时顺手清、还是一个定时动作？考虑到
  [统一动作 ABI](action-abi.md) 反对常驻进程，这条不是自动成立的。

### 2.3 落在哪里

候选：`.anas/` 下的工作区状态、`/run` 下的临时状态、systemd journal、独立文件。
特权动作的审计与非特权 job 的事件可能落在不同地方——那就又回到 §2.1 的关联问题。

### 2.4 CLI 与 Web 看到的是不是同一份

[统一动作 ABI](action-abi.md) §12 已经定了 **job 存储单一、控制台能看到 CLI 发起的 job**。
但那只解决了 job 记录本身，没解决：CLI 的人类输出、容器日志、审计条目是否也统一入口，还是
各查各的。

### 2.5 敏感值

Module Command 的 ABI 已经要求敏感参数不落日志。但事件日志会被重放、被导出、可能被贴进工单——
需要一条覆盖所有种类的统一脱敏规则，而不是每种日志各自实现一遍。

### 2.6 关联标识

一次用户操作可能横跨 CLI 输出、job 事件、特权审计与容器日志。没有贯穿的关联 id，事后就只能靠
时间戳猜。这个 id 从哪里生成、传播到哪一层，未定。

## 3. 已经确定的约束

研讨的结论必须满足这些，它们在别处已经定下：

1. **敏感参数不落日志**（Module Command ABI、[宿主特权动作通道](host-action-channel.md) §3.3）；
2. **事件日志超限必须显式标记 `truncated`**，不得静默丢弃（[统一动作 ABI](action-abi.md) §5）；
3. **审计只有一份才有意义**，不按入口分区（[统一动作 ABI](action-abi.md) §12）；
4. **不引入常驻进程**来做日志维护，除非有别的理由需要它。

## 4. 下一步

先回答 §2.1——事件与审计是一份还是两份。它是其余问题的前置：保留期、落地位置、脱敏规则都取决于
这个答案。
