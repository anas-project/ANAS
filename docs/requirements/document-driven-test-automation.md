# 文档驱动测试生成与远程执行要求

本文规定 ANAS 如何从稳定需求生成可审阅的测试用例和完整测试代码，以及如何通过 SSH 在已登记
或由用户为单次运行明确指定的服务器上自动部署、执行并收集报告。实施顺序见
[文档驱动测试自动化实施计划](/plans/document-driven-test-automation)。本主题不另设架构文档：
生成链、远程信任边界和执行生命周期都在本文中构成验收约束。

本文的需求矩阵是规范来源，正文是解释。两者冲突以矩阵为准。

## 1. 目标流程

目标流程是：

```text
需求正文与需求矩阵
  -> 机器可读的测试用例清单
  -> 可阅读的用例文档
  -> Agent 生成或更新完整测试代码
  -> 本地/远程统一运行器
  -> JSON、JUnit 与 Markdown 脱敏报告
  -> 需求覆盖和 e2e 执行证据
```

需求矩阵仍然是“系统必须做什么”的规范来源。机器可读用例清单负责把需求变成前置条件、fixture、
步骤、可观察断言和清理动作；可阅读的用例文档由该清单生成，不再手工维护第二份含义相同的正文。
测试代码可以由 Agent 根据需求与用例完整生成，不限定为脚手架。

生成完整代码不等于自动验收通过。同一个 Agent 可能同时误解需求和断言，得到内部一致但没有验证
真实行为的测试。因此生成后的代码必须和人工代码经过相同的编译、静态检查、需求溯源、反例或故障
注入、真实执行和审阅门禁。这里限制的是“生成即可信”，不是限制 Agent 写完整测试。

## 2. 用例与代码溯源

每个用例使用稳定用例 ID，并显式列出覆盖的需求 ID。用例清单至少记录测试级别、fixture/目标能力、
前置条件、执行入口、可观察断言、清理、超时和敏感数据策略。测试实现也必须声明用例 ID，使门禁可以
从需求双向追到用例、代码、执行命令和最近证据。

需求措辞或验证方式改变时，即使需求 ID 不变，相关用例也必须进入待复核状态。Agent 应根据差异提出
用例和代码补丁；不得在没有 diff 的情况下覆盖已经审阅的断言。对安全、回滚、拒绝和故障降级要求，
成功路径不足以证明行为，必须包含反例或故障注入。

## 3. SSH 测试目标

远程运行器只连接登记过的专用测试服务器，或由已授权用户为当前运行明确指定的准确 SSH 目标。
明确指定必须出现在本次调用上下文中，不能从旧报告、上次运行或模糊的环境默认值继承。目标 profile
放在 Git 忽略的本地配置中，只保存 SSH alias、远端工作根、能力标签和并发限制；私钥、密码、token、
会话文件和业务 Secret 不进入 profile、命令行、源代码包或报告。认证复用操作者的 SSH agent/SSH
config，必须验证服务器 host key，不得使用关闭 host-key 校验的参数。

SSH 账号采用最小权限。普通传输和测试进程不得获得任意 root shell；创建 network namespace、
containerd、测试 Docker daemon 或清理系统资源所需的特权必须由预安装、固定动词、固定路径的 helper
承担。远程运行前必须检查目标授权、主机能力和现有资源。未登记且没有本次明确指定的目标必须拒绝；
明确指定的目标即使承载生产服务也可以运行，但必须继续使用独立 workspace、端口、网络、containerd、
Docker socket/data-root 和定向清理，且不得接管、停止、重建或清理任何既有资源。

## 4. 一键运行生命周期

一次运行由唯一 `run-id` 标识，并依次执行：

1. 解析需求、用例、suite 和目标能力，输出无副作用计划；
2. 打包指定 commit，或打包“基准 commit + 工作区补丁”，记录内容摘要；
3. 通过 SSH 传输并校验源包摘要；
4. 在独立 workspace、端口段、网络前缀、containerd、Docker socket/data-root 中部署；
5. 执行选定测试，实时保存有界、脱敏日志；
6. 拉回报告和证据清单；
7. 只清理该 `run-id` 的容器、网络、卷、workspace 和临时凭据。

连接中断不得让运行变成不可判断状态。运行器必须能查询阶段状态、继续收集结果或显式清理。失败环境
如需保留调试，必须由调用方明确选择保留期限；到期清理仍按 `run-id` 精确执行，禁止全局 prune。

## 5. 报告与证据

每次运行同时产出机器可读 JSON、JUnit 和便于审阅的 Markdown 摘要。报告至少记录源 commit、工作区
补丁摘要、suite、用例/需求覆盖、目标能力指纹、镜像或部署摘要、起止时间、各阶段结果、清理状态和
总退出状态。报告不得包含 Secret、完整授权 URL、cookie、JWT、密码或私有 host 细节；本地敏感产物
使用 mode `0600` 并留在 Git 忽略的 `test-env/reports/` 或受控 CI artifact。

计划文档里的 e2e 执行记录只能从成功完成且身份信息完整的报告导入或据此更新，不能把“脚本存在”
当成“需求已验证”。任一必选用例失败、未执行、报告不完整或清理状态未知时，总结果不得显示为通过。

| --- | --- | --- |
| `TESTAUTO-R-001` | 需求矩阵必须继续作为行为规范来源；生成的用例文档和测试代码不得重新定义或覆盖需求语义 | 审阅 |
| `TESTAUTO-R-002` | 每个验证方式为 `单元`、`契约`、`e2e` 或 `CI` 的生效需求必须至少映射一个稳定用例 ID；只有 `审阅` 的需求可以不映射自动用例 | 单元 + CI |
| `TESTAUTO-R-003` | 用例 ID 必须在全仓唯一、分配后不复用；废弃用例必须保留 ID 和替代关系 | 单元 |
| `TESTAUTO-R-004` | 每个用例必须声明覆盖的需求 ID、测试级别、fixture/目标能力、前置条件、执行入口、可观察断言、清理、超时和敏感数据策略，缺少必填字段时门禁必须失败 | 单元 |
| `TESTAUTO-R-005` | 每个非审阅用例必须引用实际存在且可被测试框架发现的实现与执行命令，不能只登记一个计划中的文件名 | 契约 + CI |
| `TESTAUTO-R-006` | 溯源门禁必须拒绝不存在的需求/用例/文件引用、重复 ID、悬空测试实现和未被任何用例覆盖的可自动验证需求 | 单元 + CI |
| `TESTAUTO-R-007` | 人类可读的用例文档必须从机器可读用例清单生成；生成文件被手改或与清单不一致时 CI 必须失败 | 单元 + CI |
| `TESTAUTO-R-008` | 需求文字或验证方式改变后，关联用例必须由内容摘要进入待复核状态，直到用例和测试实现完成显式复核 | 单元 + CI |
| `TESTAUTO-R-009` | Agent 可以并应在需求和用例明确时生成完整测试实现，不得被流程限制为只生成空脚手架 | 审阅 |
| `TESTAUTO-R-010` | Agent 生成的完整测试代码必须通过与人工代码相同的编译、静态检查、溯源、执行和审阅门禁，生成来源不得降低验收标准 | CI + 审阅 |
| `TESTAUTO-R-011` | Agent 更新已有测试时必须给出需求、用例和代码的可审阅 diff，不得静默覆盖已经审阅的断言或人工修复 | 单元 + 审阅 |
| `TESTAUTO-R-012` | 测试必须断言需求规定的外部可观察结果，不能只把进程退出码为零、日志出现某文本或生成动作完成当作功能通过 | 审阅 + 单元 |
| `TESTAUTO-R-013` | 涉及拒绝、安全、回滚、故障降级或恢复的需求必须至少有一个反例或故障注入用例，不能只覆盖成功路径 | 单元 + CI |
| `TESTAUTO-R-014` | 新增或实质修改测试时必须证明测试能在行为缺失或被破坏时失败；无法自动做变异/反例验证时必须记录人工复核理由 | 单元 + 审阅 |
| `TESTAUTO-R-015` | SSH 目标 profile 必须位于 Git 忽略的本地配置，只保存 alias、远端工作根、能力标签和并发限制，不得保存任何认证或业务 Secret | 单元 + 审阅 |
| `TESTAUTO-R-016` | SSH 认证必须复用 SSH agent/config 并严格验证已登记 host key；运行器不得自动接受未知 host key 或关闭校验 | 契约 |
| `TESTAUTO-R-017` | 远程运行前必须验证目标已登记，或由已授权用户在本次运行中明确指定准确 SSH 目标；两者均不满足时必须拒绝。明确指定的生产主机可以运行，但不得因此绕过 R-020—R-022 的隔离与预检 | e2e |
| `TESTAUTO-R-018` | SSH 测试账号必须遵守最小权限；特权操作只能经预安装的固定动词/固定路径 helper 执行，运行器不得获得任意远程 root shell | 契约 + 审阅 |
| `TESTAUTO-R-019` | 上传源包必须对应明确 commit 或“基准 commit + 工作区补丁”，发送端和服务器端必须校验同一内容摘要并写入报告 | e2e |
| `TESTAUTO-R-020` | 每次远程执行必须使用唯一 `run-id`，并据此分配独立 workspace、端口段、网络前缀、containerd、Docker socket/data-root 和报告目录 | e2e |
| `TESTAUTO-R-021` | 服务器测试必须通过现有隔离 Docker socket 与 data-root 双重门禁，默认 Docker socket、生产 data-root 或跨 workspace Compose project 必须拒绝 | e2e |
| `TESTAUTO-R-022` | 任何部署前必须检查架构、磁盘、内存、端口、路由/DNS、目标能力和并发配额；预检失败不得开始传输后的部署变更 | 契约 |
| `TESTAUTO-R-023` | 统一运行器必须能用一个非交互命令完成计划、传输、校验、隔离部署、选定 suite 执行、报告回收和按范围清理 | e2e |
| `TESTAUTO-R-024` | 统一运行器必须支持 suite/case 选择和无副作用 dry-run；dry-run 必须显示源身份、目标、能力要求、预计资源和将执行的用例 | 契约 |
| `TESTAUTO-R-025` | SSH 中断或本地进程退出后，运行器必须能按 `run-id` 查询远端阶段、继续收集已完成报告或显式执行清理，不得把未知状态显示为失败后已清理 | e2e |
| `TESTAUTO-R-026` | 自动和人工清理只能删除当前 `run-id` 标记的资源；失败保留必须有显式期限，到期清理也不得使用全局 prune 或通用前缀匹配 | e2e |
| `TESTAUTO-R-027` | 每次运行必须同时生成结构稳定的 JSON、JUnit 和 Markdown 摘要，并能表示阶段、用例、跳过原因、清理和总结果 | 契约 |
| `TESTAUTO-R-028` | 报告必须记录源身份、suite、需求/用例覆盖、目标能力指纹、部署/镜像摘要、起止时间、阶段结果和清理状态 | 契约 |
| `TESTAUTO-R-029` | 报告、日志、源包和进程输出不得泄漏密码、私钥、cookie、JWT、授权码、API token、webhook Secret 或完整私有连接信息；本地敏感产物必须为 mode `0600` | 单元 + e2e |
| `TESTAUTO-R-030` | 任一必选用例失败、未执行、报告不完整或远端状态未知时总结果必须非零且不得显示为通过；测试失败与基础设施失败必须可区分 | 契约 + e2e |
| `TESTAUTO-R-031` | e2e 执行证据必须由身份完整的运行报告生成或导入，并关联需求 ID、用例 ID、源摘要、环境、日期和结果；脚本存在本身不算执行证据 | 契约 + CI |
| `TESTAUTO-R-032` | CI 手动触发远程测试时必须复用同一运行器，限制到允许目标和 suite，并具备审批、并发互斥、超时与 artifact 保留策略 | CI |

## 7. 明确排除

本要求不提供任意 SSH/远程 shell 产品能力，也不把私钥或服务器密码纳入仓库。默认目标仍是专用
非生产主机；已授权用户为当前运行明确指定准确服务器时允许测试生产主机，但只授权该目标，不放宽
任何隔离、最小权限、资源所有权或清理边界。本要求也不要求用确定性模板编译器代替 Agent。Agent
可以生成完整用例和测试代码，但测试结果必须来自对真实实现的独立执行证据，而不是来自生成过程对
自身输出的确认。
