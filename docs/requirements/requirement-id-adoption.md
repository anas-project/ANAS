# 需求 ID 矩阵采用范围与门禁要求

本文规定哪些需求文档必须采用稳定 ID 矩阵、未采用时门禁必须如何表现，以及需求文档改变存放位置
后门禁的扫描边界。方法论（怎么从散文抽断言、怎么选验证方式）见
[需求编写规范](/developer/requirement-authoring)，格式与目录分工见
[文档写作标准](/developer/documentation-standard) §4。实施进度见
[需求 ID 矩阵采用实施计划](/plans/requirement-id-adoption)。

本文的需求矩阵是验收规范来源，正文是解释。两者冲突以矩阵为准。

## 1. 问题：门禁的沉默

`scripts/ci/requirement-coverage.mjs` 当前对没有需求矩阵的文档执行 `continue`，既不报错也不提及。
截至 2026-08-22，`docs/requirements/` 下 6 份文档中只有 3 份（`forgejo-module`、`versitygw-module`、
`web-api-admin-console`，合计 168 项）进入校验，另外 3 份
（`iam-provider`、`module-iam-bidirectional-logout`、`vikunja-module`）被静默跳过。

**沉默才是缺陷，跳过本身不是。** 一份还没想清楚验收边界的需求文档暂时没有矩阵是正常的；问题在于
门禁通过时打印「校验通过：3 份文档，168 项需求」，读者无从判断分母应该是 3 还是 6。因此本文要求的
不是「所有文档立刻补矩阵」，而是**跳过必须是一次显式登记的决定，并在每次门禁输出中可见**。

## 2. 豁免清单

未采用矩阵的需求文档登记在一份豁免清单里，每条记录路径、理由和复核日期。清单之外的文档缺少矩阵
即门禁失败。这样「暂不采用」和「忘了写」在机器上是两件不同的事。

复核日期是给人看的：它让一份挂了半年的豁免在评审时显得刺眼，而不是永久沉底。门禁不校验日期是否
过期——那会把文档写作变成催收。

## 3. 本轮采用范围

只有 `module-iam-bidirectional-logout` 在本轮采用 ID 矩阵。它的验收对象是
`Provider × Module × 登出方向` 的组合空间，正是矩阵能约束而散文约束不住的形状：漏掉一个组合，
在散文里读起来毫无异样，在矩阵里是一个缺失的行。

`iam-provider` 与 `vikunja-module` 本轮登记豁免。前者是准入标准，其条目在接入下一个 IAM Provider
时才会被真正检验；后者对应的 Module 已经实现完毕，事后补写的矩阵只能复述代码，防不住任何当前
缺陷。**登记豁免不等于这两份文档没有约束力**——它们的正文仍然是评审依据，只是不参与机械校验。

## 4. 存放位置变更后的扫描边界

需求与计划文档将迁出 `docs/`（见[整改任务清单](/reviews/2026-08-23-comprehensive-project-audit)）。迁移期间
最危险的失败是门禁同时扫描新旧两个位置：一份文档在两处各存一份，校验都通过，而实际生效的是哪份
无人知道。因此扫描位置必须是单一的，切换是一次性的。

Module 私有的需求文档存放在各自 Module 目录下，但必须由同一个门禁覆盖——否则「把需求写到 Module
里」就成了绕过校验的合法路径。

ID 前缀在全仓范围内唯一。前缀只在单份文档内不重复是不够的：两份文档各自使用 `IAM-R-###` 时，
提交信息或测试注释里的 `IAM-R-012` 会指向两条不同的要求。

## 5. 索引状态列必须是算出来的

`requirements/index.md` 的「状态」列过去是手写的，全部条目都是「当前」——那是**文档级**状态（这份
文档仍然有效），不是完成度。完成度是**条目级**的，读索引答不了「什么没做完」。

但完成度不需要任何人再维护一个字段：需求矩阵给出全部 ID，配套计划的里程碑归属表给出「哪些 ID 属于
哪个里程碑」和该里程碑的状态。两者一 join 就是每份文档的完成度。**手写的列会在里程碑落地而索引没
被同一个提交碰到的那一刻失真；算出来的列不会。**

前提是里程碑状态列有固定词汇。现状已经接近——取 `已完成` / `实施中` / `未开始` / `阻塞` 四个之一
作为开头，分号之后允许自由文本给人读（「实施中；只读 list/detail 已完成，invoke 待办」既说明了
里程碑在飞，也说明了落地到哪）。

退出的需求不进分母：编号保留是为了不被重新分配，不代表还有人欠这份工作。

**退出标记的判定方式本身有个坑，实现本节时撞到了。** `parseRequirementMatrix` 现在用
`cells.join(' ').includes(marker)` 扫描整行，于是**一条在描述退出规则的需求会把自己判成已退出**——
`REQID-R-012` 的初稿正是因为正文里出现了那个词而被门禁报成「已退出但仍归属于某个里程碑」。
本轮先绕开（改写措辞），但正确的修法是给退出状态一个专用信号（独立列或行首标记），见
`REQID-R-014`。

## 6. 需求矩阵

| ID | 要求 | 验证方式 |
| --- | --- | --- |
| `REQID-R-001` | 需求覆盖门禁必须在每次运行的输出中列出被跳过的需求文档路径及跳过原因，不得静默跳过 | 单元 |
| `REQID-R-002` | 未登记在豁免清单中的需求文档缺少需求矩阵时，门禁必须以非零退出码失败 | 单元 |
| `REQID-R-003` | 豁免清单的每个条目必须同时具备文档路径、理由和复核日期三个字段，缺任一字段门禁必须失败 | 单元 |
| `REQID-R-004` | `module-iam-bidirectional-logout` 的需求矩阵必须为每个受支持的 `Provider × Module × 登出方向` 组合各给一条断言，不得用一条断言覆盖多个组合 | 审阅 |
| `REQID-R-005` | 该矩阵必须对每个已知不支持的 `Provider × Module × 登出方向` 组合给出一条声明其不支持的断言，不得以省略表示不支持 | 审阅 |
| `REQID-R-006` | 需求文档迁出 `docs/` 后，门禁必须只扫描迁移后的位置；同一主题的需求文档不得在两个位置同时存在 | 单元 |
| `REQID-R-007` | 门禁必须覆盖 Module 私有需求文档所在目录，其校验规则与仓库级需求文档一致 | 单元 |
| `REQID-R-008` | 需求 ID 前缀在全仓范围内唯一；两份需求文档使用同一前缀时门禁必须失败 | 单元 |
| `REQID-R-009` | 豁免清单引用的文档路径不存在时门禁必须失败，避免文档改名或删除后豁免长期悬空生效 | 单元 |
| `REQID-R-010` | 需求索引的状态列必须由需求矩阵与配套计划的里程碑状态算出，不得手工维护 | 单元 |
| `REQID-R-011` | 计划文档里程碑表的状态列必须以 `已完成` / `实施中` / `未开始` / `阻塞` 之一开头；不符合时生成器必须失败并指名该里程碑 | 单元 |
| `REQID-R-012` | 完成度分母只统计仍然生效的需求；矩阵中标记退出的行不计入 | 单元 |
| `REQID-R-013` | 索引中已生成的状态列与计算结果不一致时，文档 CI 必须失败 | CI |
| `REQID-R-014` | 需求退出状态必须由专用标记判定，不得靠扫描整行文本命中关键词 | 单元 |
