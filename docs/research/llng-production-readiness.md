# LLNG 上线范围与实现方案

用户已于 2026-10-23 确认本文完整方案；这不代表下列能力已经实现或通过验收。
用户已明确：升级最新稳定版；不需要独立恢复管理员；AD 要求下次登录改密或密码到期时，
允许已登记的 Passkey 继续登录；比较 Casdoor 与 LLNG 的服务器资源占用。
独立恢复管理员不再作为 LLNG 上线缺口。目录禁用、删除、锁定和应用撤组仍受既有 IAM 要求约束。

## 推荐上线范围

1. 升级至官方当前稳定版 2.23.4，核对升级说明，回归已有强制改密、OIDC 回跳和错误密码拒绝。
2. 复用 Samba 已有 `events.jsonl` 目录事件，增加 LLNG 消费者及持久游标；事件触发重新读取 AD，
   定位受影响会话并调用 LLNG 原生撤销流程；漏事件、重启和日志轮转以定期核对兜底。
   OIDC back-channel 和 SAML 浏览器登出按每个 Consumer 实际能力分别验收。
3. 接入原生 Passkey 首因素与设备管理。已有凭据可在密码过期或被要求修改时继续使用；
   禁用、删除、锁定账户不得借 Passkey 绕过目录状态检查。验证凭据登记、删除、重启和恢复。
4. 适配现有 user_portal：公开客户端 PKCE、近期认证、签名 auth_time、账户及应用准入检查，
   保留其现有 Samba 自助资料、改密与委派管理边界；不维护第二套业务用户目录。
5. 补齐 SAML 稳定身份锚点，使用既有应用矩阵验证准入、管理员角色、改名不换号、双向退出。
6. 通过 LLNG 支持的配置、CSS 和模板扩展点接入 ANAS 品牌及主题，保留原生认证表单。
   验证持久配置、签名密钥、Passkey 数据备份恢复和必要凭据轮换，完成发布门禁后交付可上线版本。

## Samba 事件的边界

仓库已有 Samba audit → anchor worker → 持久 `events.jsonl` 的链路，Casdoor 已消费它。
LLNG 可复用同一只读事件目录，每个消费者保存独立游标；不需要另建消息服务器。
事件只表示哪些对象和属性可能变化，权限判断仍以当前 AD 查询为准。
简单缩短 LLNG 会话有效期无法覆盖已经建立的应用会话；只删除 LLNG 数据库记录也无法保证
触发标准登出通知。实现应先验证 LLNG 原生会话撤销入口及失败行为，再确定消费者调用方式。
“实时”应落实为既有目录订阅要求中的有界传播，不能承诺跨应用零延迟。

## 复杂度与替代方案

整体复杂度为 **高**：跨 Samba、LLNG、现有门户和多个应用；涉及持久事件游标、会话与
授权状态、Passkey 凭据、跨应用登出失败处理和恢复。维护成本主要是各协议及各应用的真实
回归矩阵，而非版本号修改。推荐复用现有事件生产者、数据库、门户和原生 LLNG 扩展机制，
仅增加必要适配，避免另建目录或认证服务。上游补丁若最终不可避免，应单独说明原因及升级成本。

较简单的方案是仅升级、启用 Passkey 和验证基础 OIDC；它无法满足当前门户、已有会话撤权及
完整 IAM 验收要求，不能标记为上线完成。推荐按上述完整范围实施，分阶段记录验收结果。
完整范围的高复杂度实现已获用户确认；版本升级、既有行为回归和隔离资源测量先行。

## 资源比较方法

在用户授权的 finance 独立 Docker 环境中，使用同一测试域、相同用户规模和数据库类型，
先后运行两种 IAM，记录版本、镜像摘要、进程数、稳定空闲内存与 CPU、相同登录负载的
资源和耗时。分别列出 IAM 容器及其必要辅助进程、数据库，避免把 LLNG 的多个 worker
或 Casdoor 的目录消费者漏计。受主机共享负载影响的测量如实标注，不外推为硬件容量承诺。

## 2026-10-23 同主机资源实测

finance 独立 Docker，同一 Samba 4.23.6-r13、PostgreSQL 16、事件生产者和单个临时目录用户。
两个 Provider 依次运行；每轮重启共享依赖，4 次预热、30 秒空闲、并发 2 的 60 次全新授权码
登录/换码/UserInfo。HTTP 限于隔离 namespace，未计浏览器、TLS 和外部网络延迟。
内存为 cgroup v2 `memory.current - inactive_file`，并非进程 RSS；合计为组件中位值之和。

| 指标 | Casdoor 3.143.0-r12 | LLNG 2.23.4、2 worker |
| --- | ---: | ---: |
| IAM 主服务空闲工作内存 | 89.06 MiB | 180.52 MiB |
| 必需目录消费者空闲工作内存 | 3.02 MiB | 88.62 MiB |
| 两者合计 | 92.08 MiB | 269.14 MiB |
| 两者空闲 swap 合计 | 1.14 MiB | 0 MiB |
| 60 次登录期间 IAM + 消费者 CPU | 10.15 秒 | 21.49 秒 |
| 单次流程延迟中位数 / P95 | 1,099 / 5,799 ms | 1,578 / 2,448 ms |
| 完整请求成功 | 60/60 | 60/60 |

本轮 LLNG 加消费者空闲工作内存约为 Casdoor 的 2.9 倍，不能以“LLNG 更省内存”作为选型
理由。共享依赖另列：空闲 PostgreSQL/Samba/事件生产者分别为 Casdoor 轮 53.89/200.80/15.05
MiB、LLNG 轮 22.76/147.34/17.57 MiB；Samba 在两轮负载阶段均使用 swap。
IAM 上限均为 512 MiB，消费者 Casdoor 128 MiB、LLNG 192 MiB，共享 PG 192 MiB、Samba
512 MiB、生产者 128 MiB，未出现 OOM。Casdoor 在负载期主服务工作内存中位数降至 46.26
MiB，不能将空闲点值等同于长期保留内存。

主机为共享环境，两轮开始时 load1 为 5.20/4.11，memory pressure `some avg10` 为
3.82%/1.43%；共享服务 swap 和负载不同。因此延迟尾部不能用于推断通用性能优劣，
这也不是多用户容量或长期运行验收。两个目录消费者均使用真实持久日志，且计入资源。
原始聚合证据及精确镜像基线见配套计划；测试结束已恢复原有隔离服务。
