# AI Agent 编排设计审查

## 结论与范围

**有实质问题，建议修订后再作为实现依据。** Forgejo 作为协作面、文档按 commit 冻结、控制面与执行面分离的方向可以保留；凭据边界、实例生命周期、依赖完成条件和事件处理规则尚未形成一致契约。

基线：2026-09-05 本地工作树，HEAD `455770b`。审查对象为 [AI Agent 编排设计](../architecture/ai-agent-orchestration-design.md)，全文 853 行；同时核对配套需求、计划及当前 compute 契约。工作树已有大量未提交修改，本报告反映工作树，不代表已发布版本。下文行号均指审查时版本。

这是静态设计审查，结合 Forgejo v15 官方文档与 Codeberg 官方 SSH 说明核实相关事实；没有连接实际 Forgejo/Incus 实例，也没有运行会创建远端对象的 API probe。未验证的固定镜像行为不能视为已通过。本次只新增报告，不修改设计、需求或实施状态。

## 主要发现

### F1 · P1：用户级 SSH key 绕过按仓库限定的 token 边界

- **位置：** 设计 §4，第 378–385 行；§6.4，第 638–639 行。
- **问题与影响：** 一个 Agent 账号加入多个仓库后，通过 `/admin/users/{agent}/keys` 增加的是账号级 SSH key；API token 的 `repositories` 限定不会约束另一套 SSH 身份认证。A 仓库实例拿到该 key，即可访问该账号有权访问的 B 仓库，因此按仓库拆实例也不能实现文档承诺的跨仓库凭据隔离。Codeberg 官方明确说明，用户 key 可访问账号有权限的全部仓库，并推送到账号有写权限的仓库。[官方 SSH 说明](https://docs.codeberg.org/security/ssh-key/)
- **建议：** 执行推送优先使用仅绑定当前仓库的 HTTPS token；如保留 SSH，使用经固定版本验证的仓库级 deploy key 或每仓库独立账号，并单独核对活动归属与吊销流程。不能把“独立生成一把 key”等同于“权限限定到一个仓库”。
- **验证场景：** 同一 Agent 可访问 A、B 两仓库，A 作业凭据必须既能推送 A，又不能读取或推送 B。
- **关联需求：** `AGENT-R-006`、`AGENT-R-037`、`AGENT-R-039`。

### F2 · P1：控制面凭据矩阵缺项，计划入库和授权查询都无法按当前规则完成

- **位置：** §3.3，第 197–199 行；§4，第 382–389 行；§6.2，第 570 行；§6.3，第 619 行。
- **问题与影响：** 非执行阶段只发 `write:issue` 和 `read:repository`，却要求控制面在计划阶段通过 contents API 写文件；`write:repository` 被限制到执行阶段，管理凭据允许用途也没有包含一般计划文档提交。另一个缺口是读取 team 成员与查询他人的仓库权限：前者需要组织读取能力，而指定仓库 token 不允许组织 scope；后者属于仓库管理能力，不能假定普通 write collaborator 的受限 token 可用。[Forgejo v15 token 权限说明](https://forgejo.org/docs/v15.0/user/authentication/token-scope/)
- **建议：** 为“协作回写、文档发布、权限读取、身份引导、作业推送”列出明确的账号、scope、仓库范围、持有组件和生命周期。文档发布可以持有仅在控制面的仓库写凭据，但必须明确它与执行凭据的区别；授权查询也须有独立且允许使用的凭据路径。
- **验证场景：** 从未批准执行的 issue 能提交计划文档；控制面能查询实际触发人的权限；工作实例仍看不到文档发布和权限读取凭据。
- **关联需求：** `AGENT-R-006`、`AGENT-R-008`、`AGENT-R-024`、`AGENT-R-031`、`AGENT-R-032`。

### F3 · P1：compute 接入描述仍依赖已删除的运行时接口

- **位置：** §5.1，第 409–413 行；§5.2，第 421–423 行。
- **问题与影响：** 设计称 compute Contract 定义实例生命周期，并在图中使用 `exec_stdin`。当前 [compute 契约](../../contracts/compute/README.md) 只有 `ensure`、`inspect`、`revoke`，负责在 apply 时交付 project、配额和受限证书；实例创建与执行由消费者驱动。[Incus 计划 M0](../../dev-docs/plans/incus-module.md) 还明确解释：旧 Provider ABI 没有 stdin 流，已移除旧运行时操作。照本文实现将依赖不存在的接口。
- **建议：** 图中分开“apply 时获取沙箱租约”与“运行时使用租约连接 Incus”，说明消费者客户端负责 create/exec/stop/delete、Secret stdin 通道与清理。同步更新依赖里程碑；当前系统容器对应 M7，本文第 434 行仍写 M5。
- **验证场景：** 控制面重启后仅凭持久化租约和作业记录，可以重新连接已有实例、取消及回收，无需每个作业触发 Provider operation。

### F4 · P1：默认共享仓库实例与取消即销毁实例相冲突

- **位置：** §5.6，第 489–503 行；§3.1 前的交互表，第 67 行；§3.6，第 295 行。
- **问题与影响：** 默认 `repo` 档让同仓库多个 issue 共用实例，又允许 `/queue parallel n`，但取消要求销毁实例。若 A、B 在同一实例执行，取消 A 会一并中止 B；即使执行串行，也可能破坏另一 issue 的讨论会话。§5.1 又描述每 Agent 一个常驻讨论容器，与 §5.6 的按仓库实例不一致。
- **建议：** 先统一默认实例模型。共享实例必须定义作业进程树、凭据与 worktree 的单独清理，等实例无活跃使用者后再销毁；若取消必须销毁执行边界，则采用独立作业实例。不能同时保持上述默认规则而不定义例外。还应说明同实例内讨论只读与执行写凭据之间如何隔离。
- **验证场景：** 同仓库 A、B 并行，取消 A 后 B 的进程、工作区和凭据均保持有效，A 无残留执行和可用凭据。
- **关联需求：** `AGENT-R-037`、`AGENT-R-039`、`AGENT-R-043`、`AGENT-R-049`。

### F5 · P1：把失败关闭当成依赖完成，会错误放行后续任务

- **位置：** §3.7，第 322–335 行；§8.2，第 745–747 行；§3.6，第 282、296 行。
- **问题与影响：** 执行 issue “完成或失败即关闭”，作业结束后解除父依赖；调度又把 issue 关闭用作前置完成信号。因此 A 执行失败后关闭，等待 A 的 B 可能继续执行。另一个未定义的边界是 PR 已创建但尚未合并：若 B 依赖 A 的代码进入目标分支，仅成功开 PR 也不能解除该代码依赖。
- **建议：** 区分作业终止、执行成功、PR 待审、变更已合并与依赖满足。失败或取消默认保持依赖阻塞；明确每种依赖要等成功产物还是目标分支合并，不能仅依赖 issue 的 open/closed。
- **验证场景：** A 失败、取消、仅开 PR、PR 合并四种情况分别校验 B 是否可运行。
- **关联需求：** `AGENT-R-041`、`AGENT-R-047`、`AGENT-R-048`。

### F6 · P1：按 Agent 作者全量丢弃事件，会切断圆桌讨论

- **位置：** §7，第 674 行；§3.2，第 177–185 行；§8.1.0，第 704–713 行。
- **问题与影响：** 入口要求忽略所有 Agent 账号事件，而圆桌要求主持通过评论 `@` 其他 Agent，并让主持接收其回复。按前一条实现，主持提问与其他 Agent 回答均在入口被丢弃，后面的 provenance 上下文过滤没有机会工作。控制面若在内部调度这些消息也可以成立，但本文没有定义这条独立路径及其持久化、授权和恢复规则。
- **建议：** 区分展示回写、工具状态、主持委派及讨论回复。展示事件去重忽略，合法委派和回复进入显式内部消息流程，并继承人类发起人的授权、预算和轮数上限；webhook 回声不能再生成第二次委派。
- **验证场景：** 主持问一次、另一 Agent 回答一次、主持汇总一次；这些评论的 webhook 各重投十次，既不漏回合，也不自增长。
- **关联需求：** `AGENT-R-014` 与 `AGENT-R-022` 当前也需要同步消除冲突。

### F7 · P1：基线变化既撤销批准又触发执行，事件路径没有确定语义

- **位置：** §3.3，第 206–207 行；§3.6，第 277–285 行；§7，第 668–673 行。
- **问题与影响：** 批准绑定 commit，基线变动必须重新批准；但 `on:push` 又承诺“基线更新后重新执行”。使用新 SHA 会违反原批准，继续使用旧 SHA 则没有在新基线上执行。且 §7 的实际订阅清单遗漏 `push`，与“已经订阅”的断言不符。
- **建议：** 明确事件只唤醒作业还是允许更换执行基线。按现有冻结规则，新基线应进入重新规划/批准；如允许预授权更新，必须单独定义授权对象和范围。补上所需订阅，将计划文档 SHA、代码基线 SHA 和批准快照分开存储。
- **验证场景：** 批准 SHA A 后收到推送 B，系统必须给出唯一、可审计的结果，不能有时继续 A、有时自动执行 B。
- **关联需求：** `AGENT-R-028`、`AGENT-R-048`。

### F8 · P1：inbox/outbox 和租约尚不足以保证外部副作用恰好一次

- **位置：** §5.6，第 524 行；§7，第 672–674 行；§10，第 776 行。
- **问题与影响：** 文档以 inbox 去重、租约和 outbox key 保证重复投递只产生一次评论/PR/commit，但未说明幂等键如何被 Forgejo 接收或如何恢复不确定结果。典型情况是 Forgejo 已创建评论，控制面在保存 comment ID 前崩溃；重放本地 outbox 仍可能再次创建。租约过期也不等于旧工作进程已停止，接管后可能有两个进程推送。
- **建议：** 按外部操作定义可查询的业务标识、响应丢失后的查回方式、唯一性及冲突处理，并定义租约代次如何阻止旧执行者继续写入。`updated_at` 对账另须规定无法找回批准人或冻结快照时拒绝恢复执行；只看到 `ai:approved` 当前存在不能重建有效授权。
- **验证场景：** 在远端接受写入与本地确认之间杀死控制面；模拟租约过期但旧进程存活；丢弃批准 webhook 后对账。结果应无重复产物，也不能凭当前标签补造批准。
- **关联需求：** `AGENT-R-012`、`AGENT-R-013`、`AGENT-R-035`、`AGENT-R-044`。

### F9 · P2：自定义工作分支破坏“不用分支锁”的前提

- **位置：** §5.6，第 519–526 行；§6.4，第 630 行。
- **问题与影响：** 不加锁的依据是不同 issue 一定使用不同分支，但配置允许用户指定工作分支，没有限制两个 issue 指向同一分支。允许并行后，可能出现同分支 worktree 创建失败、交错提交或推送冲突；只锁 `ai:direct` 的目标分支覆盖不了该情况。
- **建议：** 为工作分支建立 `(repo_id, branch)` 的活跃归属约束，重复使用时拒绝或串行；如要强制每 issue 独立分支，应明确自定义名也必须满足唯一性。
- **验证场景：** 两个 issue 都指定 `ai/shared` 并请求并行，第二个必须在执行前得到明确的冲突结果。
- **关联需求：** `AGENT-R-038`、`AGENT-R-049`。

### F10 · P2：思考强度同时被规定为“不得进标签”和“必须进标签”

- **位置：** §3.2，第 165–169 行；§5.5，第 469–472 行；§3.9，第 371–374 行。
- **问题与影响：** 前文明确模型和思考强度只存库、不写标签，后文却要求使用 `ai:effort/<agent>=<原生值>`，并把 `/model`、`/effort` 包进“命令执行后写回对应标签”的总规则。实现无法同时满足，需求矩阵 `AGENT-R-020` 与 `AGENT-R-023` 也有相同张力。
- **建议：** 保留参数存库与状态评论展示，删除 effort 标签示例；把“命令与标签等价”限定到确有标签对应的流程控制命令，运行参数命令单独描述。

## 其他应同步澄清的内容

- **权限术语：** 第 560 行的 `maintain` 不在 Forgejo v15 官方列出的 Read、Write、Administrator、Owner 四档协作者权限中；组织 team 还可按 Code、Issues 等单元分配权限。应定义实际 API 返回值到动作集的映射，不能照搬单一仓库角色名。[Forgejo v15 仓库权限](https://forgejo.org/docs/v15.0/user/collaboration/repo-permissions/)
- **表单字段矛盾：** 第 45 行称 front matter 支持 `assignees`，第 110 行又明确不能自动指派；固定镜像验证后统一结论。
- **数据关系：** 第 323 行允许一个方案派生多个作业，第 524 行却用 `(issue, plan_version)` 唯一性；表结构未区分 topic issue、execution issue、逻辑 job 与重试 attempt。应先确定各自 ID 和映射，避免去重误拒合法拆分，或按新执行 issue 去重却遗漏父计划重复派发。
- **文档状态漂移：** 第 843–844 行仍称需求与计划将在评审后产出，但两份文件已存在。计划索引将 `ai-agent.md` 放在“已归档”表中，状态却为提案，也会误导后续阅读。

## 修订顺序

先解决 F1–F8 的凭据、执行和状态流转问题，再修 F9–F10 及术语、数据关系与状态漂移。涉及生命周期、失败依赖和基线更新的选择需要明确产品行为，再同步设计、需求矩阵与实施计划；不能只修设计正文，留下相冲突的验收标准。上述验证场景应随相应实现落入测试，当前报告不宣称它们已经通过。
