# 开源自部署应用研究 Module 规范

本规范供 ANAS 维护者持续研究某一类开源自部署应用。它定义候选发现、事实核验、比较口径、评分和交付物；后续研究“相册”“密码管理”“笔记”等主题时均应复用，而不是临时设计表格。

> [!NOTE]
> 状态：当前研究流程。规范版本 `1.1`，基线日期 2026-08-13。这里的 “Research Module” 是研究工作单元，不是可部署的 `modules/*` Runtime Module。1.1 增加头部商业基准反向发现，以及社区自部署/付费版边界。

## 1. 研究主题定义

每轮开始先写一份主题卡，避免“所有”“支持”“开源”等词在研究中途改变含义。

```yaml
topic: notes
title: 开源自部署笔记应用
snapshot_date: 2026-08-13
decision_for: ANAS module 候选
must_be:
  - 可获得源代码并允许自行部署
  - 核心用途属于本主题，或在相邻候选中明确标注
  - 上游仍可访问
deployment_target:
  os: Linux
  runtime: Docker Engine + Docker Compose v2
  ingress: Traefik HTTPS
  architectures: [amd64, arm64]
questions:
  - 哪些项目值得进入 Module PoC？
  - 社区版能否接 ANAS IAM？
  - 能否复用已有数据库和存储能力？
```

主题卡还必须定义：核心类别、相邻类别、明确排除项、目标用户、预期规模和检索日期。“当前所有”表示在已声明来源和检索式下尽可能完整的可复核候选集，不表示数学意义上永不遗漏。

## 2. 范围与分类

候选使用漏斗分类，任何被发现的项目都应有去向：

1. **核心候选**：严格符合主题、开源且可自部署。
2. **相邻候选**：可完成主要任务，但产品定位更偏 wiki、文档协作、白板或完整工作空间。
3. **源码可见/开放核心**：许可证不是 OSI/FSF 通常意义的开源，或关键自部署能力只在商业层。
4. **停止/不成熟**：归档、长期无有效发布、上游明确 alpha/beta 或不建议生产。
5. **排除**：SaaS-only、仅客户端且不存在可部署服务、仅静态文件发布、与主题偏离，或无法确认许可证。

同一项目可能有客户端、同步服务、Web 前端和企业扩展多个仓库。研究对象是完整可用拓扑，Star 不能只挑最大的客户端仓库而忽略不成熟的自托管服务。

## 3. 候选发现

### 3.1 目录来源

每轮至少使用三个相互独立的发现源：

- [AlternativeTo](https://alternativeto.net/)：用 `Open Source`、`Self-Hosted` 和主题标签组合检索；优点是平台和用户热度，缺点是许可证及状态可能滞后。
- [selfh.st Apps](https://selfh.st/apps/)：可按用途、Star 和最近活动浏览自托管应用。
- [awesome-selfhosted](https://awesome-selfhosted.net/)：社区维护的严格自托管目录，适合发现轻量项目。
- [Libre Self-hosted](https://libreselfhosted.com/) 与 [AwesomeHub](https://awesomehub.js.org/list/selfhosted/)：用于补漏，不作为最终事实来源。
- GitHub/GitLab/Codeberg 的主题、代码和发行搜索：补充新项目、分叉和已更名项目。

还应搜索主要商业产品的“open source/self-hosted alternative”，并检查聚合站的下一页。目录条目只证明“值得调查”，不能证明项目确实开源、仍活跃或具备某项功能。

### 3.2 从头部闭源产品反向发现

按主题先列出 3–8 个用户最熟悉的闭源/商业基准，再分别打开其 alternatives 页面并组合 `Open Source + Self-Hosted` 过滤器。这一步是必做项，不能只搜索聚合站的宽泛主题标签。例如笔记主题至少应从 Obsidian、Notion、Evernote、Microsoft OneNote 和 Google Keep 反向检索：

```text
AlternativeTo /software/obsidian/?license=opensource&platform=self-hosted
AlternativeTo /software/notion/?license=opensource&platform=self-hosted
AlternativeTo /software/evernote/?license=opensource&platform=self-hosted
```

每个基准记录其核心卖点（例如 Obsidian 的 local-first/双链/插件，Notion 的数据库/协作），用于发现候选和建立场景，不把闭源产品放进严格开源排名。还要打开重要开源候选自身的 alternatives 页面形成第二跳；这能发现主题总表漏标或错误标注为“非自托管”的项目。

### 3.3 去重与身份解析

- 记录 `project_id`、现行名称、旧名、官网、主仓库、服务端仓库和许可证文件。
- 合并旧项目与官方继任者，例如原项目转为社区 fork 时保留迁移说明。
- fork 只有在具有独立维护、发布或产品方向时才单列。
- 同一产品的客户端 Star 和服务端 Star 分开记录，并标注主表采用哪个数。

建议先维护候选台账，再开始逐项深挖：

| 字段 | 含义 |
| --- | --- |
| `discovered_from` | 首次发现的目录或检索式 |
| `scope_class` | core / adjacent / source-available / stopped / excluded |
| `repository` | 作为活跃度基准的仓库 |
| `reason` | 纳入、降级或排除的一句话理由 |
| `evidence_status` | verified / partial / unverified |

## 4. 证据规范

### 4.1 来源优先级

1. 当前版本的许可证、官方文档、配置 schema、Compose/Helm 文件和 API 规范；
2. 官方仓库 README、release、changelog、issue/讨论中的维护者声明；
3. 官方镜像 registry 元数据与支持架构；
4. GitHub/GitLab/Codeberg API 的动态仓库数据；
5. 聚合目录、独立评测和社区讨论。

关键结论至少有一条一级或二级证据。社区讨论可说明实际体验，不能单独证明 SSO、许可、备份或生产支持。

### 4.2 冲突处理

- LICENSE 与营销文案冲突时，以 LICENSE 和具体目录的许可边界为准。
- 文档与当前 Compose 冲突时，以锁定 release 的文件为准，并记录文档漂移。
- 聚合站写“有 App”，上游只说 PWA 时，写 PWA，不写原生 App。
- 没找到证据写“未确认”；只有官方明确不存在或架构上确实没有时才写“不支持”。
- 记录事实采集日。Star、最后 push、最新版本和商业功能边界超过 90 天必须重查。

## 5. 统一字段字典

### 5.1 产品与平台

| 字段 | 记录规则 |
| --- | --- |
| 定位 | 个人笔记、团队协作、知识库等一个主定位，避免堆功能词 |
| 许可证 | SPDX；开放核心需说明社区/企业目录边界 |
| Web | 区分完整编辑 Web、仅管理页、只读发布页和静态 Web 构建 |
| 桌面 | Windows/macOS/Linux 分列；注明原生、Electron/Tauri 或第三方 |
| 移动 | Android/iOS 分列；注明官方原生、第三方、PWA 或移动网页 |
| 离线/同步 | local-first、服务端实时、WebDAV、文件同步和 E2EE 分开描述 |
| 多用户 | 单用户、多账号隔离、协作编辑和公开分享不是同一能力 |

### 5.2 自部署与依赖

记录官方镜像/tag、Compose/Helm、amd64/arm64、反向代理要求、端口、持久化目录、数据库、缓存、队列、对象存储、搜索、SMTP、转码/AI 服务和最低资源。依赖分为：

- **必须**：没有就不能运行；
- **生产建议**：测试可省略，生产文档要求；
- **可选功能**：附件、全文搜索、邮件、AI 等；
- **外部联网**：启动时下载模型/资源、许可证校验、遥测或 SaaS API。

同时给出数据备份面和恢复面，不能只数容器数。

### 5.3 身份与 SSO

“社区版支持 SSO”只在免费自部署版本原生支持 LDAP、OIDC/OAuth2 通用 Provider、SAML 或可信代理认证时标 ✅，并写协议：

- 社交登录模板不自动等于通用 OIDC；
- 反向代理 Basic Auth 不等于应用账号 SSO；
- oauth2-proxy 能保护入口，但不能自动解决用户映射、API、移动端和 WebSocket；
- 第三方插件标 ◐，商业版专属标 `企业版`；
- 核验首次登录自动建号、账号绑定、组/角色映射、禁用本地登录、单点登出和移动客户端兼容性。

### 5.4 API、自动化与 AI

API 分为官方稳定公共 API、内部/未承诺 API、客户端本地 API、插件 API、Webhook、CLI 和 MCP。对每项记录认证方式、OpenAPI/版本化、读写范围和服务端可达性。

AI 使用以下等级：

- **A 原生可自选模型**：支持 OpenAI-compatible/Ollama 等，且可在社区自部署版配置；
- **B 原生但受限**：只支持指定云、商业层或部分能力；
- **C 可集成**：无内置 AI，但稳定 API/Webhook/MCP 足以外接；
- **D 困难**：只有 UI 自动化、文件扫描或非稳定内部接口。

另行记录 RAG/向量库、Embedding、模型下载、GPU、数据外发和 API Key 保存方式。

### 5.5 社区、活跃度与成熟度

Star 是快照信号，不是质量分数。至少同时采集：仓库创建日、最后 push、最近 release、release 是否稳定、归档状态、近 90/365 天提交与发布、issue/PR 响应、维护者数量、升级文档和安全政策。

统一评级：

| 维度 | 高/成熟 | 中/成长 | 低/早期或停止 |
| --- | --- | --- | --- |
| 活跃度 | 90 天内持续多人提交并有 release | 有维护但节奏不稳定或主要为单维护者 | 超过一年无有效发布、归档或明确停更 |
| 成熟度 | ≥3 年、稳定 release、升级/备份/安全文档和生产案例 | 1–3 年或关键运维契约仍在形成 | alpha/beta、破坏性变化频繁或上游声明不适合生产 |

自动依赖更新、翻译同步和镜像重建不能单独作为“开发很活跃”的证据。

### 5.6 社区版、付费版和使用限制

“代码开源”“可以免费自托管”“官方托管免费套餐”和“企业支持”是四个不同概念。每个候选必须增加商业边界记录：

| 字段 | 必须回答的问题 |
| --- | --- |
| 开源自部署社区版 | 哪些仓库/镜像构成可用系统，是否需要许可证 Key、订阅或联网授权？ |
| 官方免费托管 | 是否存在，用户数、存储、附件、版本历史、AI 配额等限制是什么？ |
| 官方付费版 | 付费增加托管容量、同步、SSO、审计、AI、支持，还是包含不开源代码？ |
| 企业版差异 | OIDC/SAML/LDAP、组同步、RBAC、审计、保留策略和 HA 是否被锁定？ |
| 自部署限制 | 用户/空间/设备/功能上限，商标条款，禁止托管服务，官方镜像可用性和支持状态 |
| 隐性外部依赖 | 即使自部署仍依赖厂商账号、Cognito/Cloudflare、License Server、云 AI 或官方插件市场吗？ |

只写“免费/付费”不够。若上游没有统一功能矩阵，应写“未确认”，并指出需要在锁定 release 上测试的 entitlement。官方 SaaS 的容量限制不能误写成社区自部署限制；反过来，AGPL 仓库存在也不能证明企业目录里的 SSO/审计代码属于社区版。

## 6. ANAS 适配评估

每个核心候选回答：

- 能否直接使用固定版本官方多架构镜像？
- 能否复用 `traefik`、现有 IAM、`relational_database` Contract、Nextcloud 或未来对象存储能力？
- 身份协议应声明哪个 `requires_capabilities`，能否自动注册 client？
- 数据属于 `data/` 还是 `userdata/`；备份、恢复、快照和降级边界是什么？
- 初始化是否必须交互；管理员账号和 Secret 如何生成、轮换与回收？
- 健康检查、升级迁移、版本锁和回滚保护是否可自动化？
- 新增依赖是否具有跨应用复用价值，还是应用私有负担？

适配等级：`A` 可优先 PoC；`B` 可选但有明确成本；`C` 仅专项需求；`D` 不建议。等级必须附一句原因，不能只给字母。

## 7. 执行流程

1. 写主题卡和纳入/排除规则，并列出头部闭源/商业基准。
2. 从至少三个主题目录及每个头部产品的 filtered alternatives 页面建立长名单，保存发现来源和别名。
3. 核验许可证与真实自部署路径，完成第一次分层。
4. 读取每个核心候选的官方 README、部署、认证、API、备份和升级资料。
5. 通过仓库 API 在同一天采集动态指标。
6. 填主表和“社区自部署 vs 官方付费”表；证据不足的格子标 `未确认`，形成待核验清单。
7. 对 A/B 级候选做源码/Compose 深查；必要时部署 PoC，记录 CPU、RAM、镜像体积、启动和恢复测试。
8. 给出场景化结论，不制造单一“总冠军”。
9. 把结果写入 `docs/research/<topic>-research-YYYY-MM-DD.md`，更新研究索引和侧边栏。
10. 实施 Module 后，将稳定事实提升到 reference/guide；研究报告保留为日期快照。

## 8. 交付模板

一份完整报告至少包含：结论先行、范围与局限、发现来源、头部商业基准、严格开源主表、社区自部署/付费差异表、相邻/非开源/停更表、重点候选详评、ANAS 适配建议、PoC 清单、排除清单、动态数据明细和上游来源。

主表建议拆成“产品能力”和“部署集成”两张，避免一个超宽表掩盖限制。符号统一为：✅ 官方原生；◐ 有限制/插件/早期；❌ 官方明确不支持；— 未确认或不适用。

## 9. 发布前检查

- [ ] “所有”的检索边界、日期和遗漏风险已说明。
- [ ] 每个发现项目进入核心、相邻、非开源、停止或排除之一。
- [ ] 已从主要闭源/商业基准的 filtered alternatives 页面做反向检索和第二跳补漏。
- [ ] 许可证、部署、SSO、API、依赖和 AI 均有上游证据或明确标未确认。
- [ ] Web、PWA、原生 App、管理 UI 和同步服务器没有混写。
- [ ] Star 与时间来自同一天快照，客户端/服务器仓库没有偷换。
- [ ] 社区版与企业版、核心功能与第三方插件边界清楚。
- [ ] 免费自部署、官方免费托管、付费托管和企业私有功能没有混写，使用限制有证据。
- [ ] 结论覆盖 ANAS IAM、数据库、入口、持久化、备份、升级和架构。
- [ ] 外部链接可访问，文档已加入索引和侧边栏。
- [ ] 已运行 `npm run docs:build`。
