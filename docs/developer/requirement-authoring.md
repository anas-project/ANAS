# 需求编写规范

本文说明**怎么产出**一份可追溯的需求矩阵。文档放在哪个目录、ID 有什么性质、检查表长什么样，见[文档写作标准](/developer/documentation-standard) §4；本文只讲方法。

## 1. 生成顺序：矩阵是最后一步

按下面的顺序做。**颠倒顺序是最常见的失败**：一上来就填矩阵会产出一堆听起来正确、但没有约束力的条目，因为此时还不知道哪些地方真的会出错。

1. **先调研和讨论。** 读代码确认现状，读既有契约确认边界，把方案的替代选项和否决理由讨论清楚。这一步的产出是判断，不是文档。
2. **写散文。** 把结论、理由、被否决的方案写成正文。理由必须写——它是以后避免重新讨论的唯一依据，而矩阵里放不下。
3. **从散文抽原子断言。** 见 §3。这一步几乎总会发现散文里有含糊的地方，回去改散文。
4. **给每条定验证方式。** 见 §4。定不出来的，通常是断言还不够具体。
5. **分配里程碑并跑校验。** `npm run docs:check-requirements`。

第 3 步之所以在第 2 步之后，是因为**抽取本身是一次审查**。把「一旦提供过 HTTPS 就不再回退明文，即使证书事后消失」变成一条可判真假的断言时，你会被迫回答「那消失时到底怎么办」——散文可以糊过去，断言不行。

## 2. 一条需求的判据

四条同时满足才是需求：

- **可证伪。** 能说清什么情况算违反。「应当考虑性能」不可证伪，「列表端点必须支持 `limit` 与 `cursor`」可以。
- **原子。** 一条断言只描述一件会独立出错的事。用「且」「并」连起来的，如果两半可能分别失败，就拆开。
- **说不变量，不说机制。** 写「管理面必须在被管理系统停机时仍可达」，不写「用固定端口实现」——除非机制本身就是要求（例如「ETag 必须使用 `managedConfigState.Digest`」，重点正是不许另造一个摘要）。
- **主语具体。** 谁必须做到？`anasd`、前端、发布流水线、还是审阅者。主语模糊的条目没人认领。

## 3. 从散文抽断言

四条操作规则：

**去掉理由。** 「若直连永远只有有限功能，则 IAM 故障时管理员只剩一个残废的控制台——到达完整级后，两个门给出相同的能力。」破折号前是理由，留在正文；断言只有后半句。

**拆开复合句。** 「到达完整级后引导级永久关闭：token 作废，端点返回 404，重开只能从 CLI」是三件会分别出错的事，拆成两到三条（token 失效是一条，端点行为与重开路径是另一条）。

**补全隐含主语和条件。** 散文里「不得回退」在上下文中很清楚，抽出来必须写成「提供过 HTTPS 后不得回退明文 HTTP；证书消失应报错」。

**不要为凑数编号。** 背景、动机、对既有契约的复述都不编号。判断方法：删掉这一条，有没有任何行为可以合法地改变？没有就不是需求。

## 4. 验证方式怎么选

问一句：**要观察到它被违反，最低成本的手段是什么？**

| 方式 | 适用 | 例 |
| --- | --- | --- |
| `单元` | 能在进程内断言 | 伪造「证书消失」不得回退引导级 |
| `契约` | 需要检查 HTTP 响应或 CLI 输出的形状 | 配置写入冲突返回 `412` |
| `e2e` | 需要真实 Docker、Btrfs、域名或主机 | 停掉 IAM 后本地账号仍可登录 |
| `CI` | 是构建或流水线的属性 | 同一 commit 两次构建产出相同归档 |
| `审阅` | 无法自动判定：架构边界、文档措辞、设计意图 | 不得为每个 Module 编写独立 HTTP 适配 |

**`审阅` 的比例是一个自检信号。** 它越多，说明需求写得越抽象、越难在实现时被真正约束。作为参照，管理控制台的 100 条里 `单元` 38%、`审阅` 32%、`e2e` 15%、`契约` 12%、`CI` 3%——32% 已经偏高，其中一部分本可以写得更具体从而变成可自动判定的条目。超过三分之一时应当回头看看能不能改写。

## 5. 需求从哪来

不要凭空构思。这四个来源覆盖绝大多数条目：

- **代码现状。** 读实现能发现真正的阻塞项。「运行时锁是阻塞 flock，守护进程里必须改成非阻塞」这类要求只可能来自读代码。
- **既有契约与设计。** `reference/contracts/`、`architecture/` 中已经定下的边界，新特性不得破坏。
- **被否决的替代方案。** 每否决一个方案，通常对应一条「不得如此」的需求，以及决策记录里的一行理由。
- **产品规模决策。** 「面向家用与小型公司」直接决定了角色分层这类取舍。

## 6. 常见反模式

| 反模式 | 问题 | 改法 |
| --- | --- | --- |
| 把里程碑写进需求 | 「M4 之前必须决策」——需求文档不认识里程碑 | 改写成条件：「实现快照写操作之前必须决策」 |
| 复述 CI 已经门禁的事 | 「必须通过 `go vet`」对每个特性都成立，不是本特性的需求 | 删掉 |
| 一条需求描述整个子系统 | 无法判定完成，也无法定验证方式 | 拆成若干条各自可测的断言 |
| 只在正文写、忘了进矩阵 | 正文是解释，矩阵才是规范来源，不进矩阵等于没有约束力 | 抽取后核对一遍散文里的每个「必须／不得」 |
| 进了矩阵但没分配里程碑 | 永远不会被验收 | `docs:check-requirements` 会拦住 |

## 7. 需求变化时

- **改措辞**：直接改矩阵那一行，ID 不动。
- **加需求**：分配新序号（不复用旧号），同步补进计划文档的归属表。
- **废弃需求**：保留该行并标 `已废弃`，不删除、不复用编号；同时从归属表移除。旧提交与测试里引用的编号必须仍能查到它当初是什么。
- **拆分需求**：原条目标 `已废弃`，新增两条新编号，在废弃行里写明被哪两条取代。

每一种都要跑 `npm run docs:check-requirements`，再跑 `npm run docs:requirement-status`——
增删需求或标记退出会改变索引的完成度，那一列是生成的，见
[文档写作标准](/developer/documentation-standard) §4。

## 8. 从需求生成测试用例

需求矩阵与同名实施计划完成后，Agent 读取需求全文、矩阵、计划和引用契约，在
`test-env/cases/<主题>/cases.yml` 中生成机器可读用例。矩阵决定“必须验证什么”，计划提供里程碑、
环境和已有执行入口；fixture、前置条件、步骤、外部可观察断言、反例和清理由 Agent 补全，不能只机械
复制两张表。

把本轮采用的需求放入 `requirement_scope`。每个自动验证需求至少映射一个 active 用例，`e2e` 需求至少
映射一个 e2e 级用例；测试实现文件必须用 `TEST_CASES:` 反向声明用例 ID。Agent 可以直接生成完整测试
代码，不限于脚手架，但生成代码仍要通过反例/故障路径、真实执行和普通代码审阅。

```bash
npm run test-cases:digests
npm run test-cases:generate
npm run test-cases:check
```

`cases.yml` 是测试设计的机器来源，同目录 README 是生成视图，原始执行报告进入 Git 忽略的
`test-env/reports/`。需求正文或验证方式改变后摘要会失效；先复核用例和测试断言，再更新摘要，不能用
批量刷新掩盖语义变化。
