# 文档写作标准

本标准适用于 `docs/` 中所有新增和修改内容。提交文档前，先确定读者、文档类型和事实来源，再决定目录与写法。

## 1. 先分类，再创建文件

| 目录 | 主要读者 | 内容 | 不应包含 |
| --- | --- | --- | --- |
| `getting-started/` | 第一次使用者 | 安装、前置条件、最短可用路径 | 完整参数表、内部实现 |
| `guide/` | 普通用户 | 按任务组织的配置和日常操作 | 未实现设计、调研过程 |
| `operations/` | 管理员 | 运行维护、故障处理、服务专项说明 | 开发实现细节 |
| `operations/runbooks/` | 值班管理员 | 有前置检查、风险和恢复步骤的主机操作 | 没有验证或回退的危险命令 |
| `reference/` | 用户和开发者 | 参数、Module、环境变量等可查询事实 | 推测、教程式长叙述 |
| `reference/contracts/` | 工具和集成开发者 | 稳定 CLI、JSON、文件格式契约 | 未落地的目标接口 |
| `developer/` | 贡献者 | 仓库、Module、测试、发布和文档流程 | 用户操作手册 |
| `requirements/` | 产品和架构维护者 | 目标、范围、硬约束和验收标准 | 候选比较、实现步骤、阶段进度 |
| `architecture/` | 维护者 | 当前模型、设计决策和明确标注的演进方案 | 未标状态的未来命令 |
| `plans/` | 实施负责人 | 已明确目标的里程碑、迁移顺序和剩余工作 | 当前操作说明、外部候选调研 |
| `research/` | 决策者 | 外部事实调研、候选比较和技术选型 | 需求、实施计划、历史审查、当前操作说明 |
| `reviews/` | 维护者和审查者 | 绑定日期、版本或提交基线的审查与实施评估 | 持续维护的架构或操作说明 |
| `governance/` | 社区和维护者 | 项目治理、注册和政策资料 | 服务配置指南 |

一个主题可能涉及多类文档，但不要复制整段内容。用户指南说明“怎么做”，参考文档列出“有哪些”，设计文档解释“为什么”；用链接连接它们。

## 2. 中英文规则

- 新增或修改面向用户的 `getting-started`、`guide`、`operations` 和核心 `reference` 页面时，必须同步维护 `/en/` 下的英文镜像。
- 中英文文件使用相同的相对路径和章节结构，便于切换与审查。
- AI Agent、生成脚本和其他自动化也必须遵守同一规则：一次任务中同时创建或更新中文页与 `docs/en/` 镜像，不能先生成单语页面并把翻译留给后续任务。
- 生成器必须把中英文文件视为同一个原子输出集合；`--check` 需要在任一文件缺失或过期时失败。新增生成页面时必须为两种语言同时添加测试和侧边栏入口。
- 中文是详细架构设计的当前源语言。暂时无法完整翻译架构或调研时，至少更新 `/en/architecture/` 或 `/en/research/` 的英文索引摘要，并明确链接到中文原文。
- 不要逐词硬译命令、配置键、Module 名、文件路径或错误码；这些技术标识在两种语言中保持一致。
- 两种语言必须表达相同的支持状态、风险和默认值。

## 3. 准确性与状态

按以下优先级确认事实：

1. Runner 代码、配置 schema 和测试；
2. `modules/*/module.yml`、Compose 文件和 Hook；
3. `docs/reference/contracts/` 中的稳定契约；
4. 当前指南和设计文档。

不要仅根据旧文档复制命令或默认值。提交前实际运行示例命令的 `--help`、解析或相关测试。版本、Module 状态、参数数量等容易变化的内容应注明来源或复核日期；能够链接到权威清单时，不重复维护易漂移的列表。

Module 与 Contract 的源文件、必需章节、生成标记、VitePress 镜像、双语和 CI 规则分别以 [Module 文档生成标准](/developer/module-documentation) 与 [Contract 文档生成标准](/developer/contract-documentation) 为准。生成镜像不得直接编辑；Module 的版本化时区和语言事实以 `modules/*/localization.yml` 为准。

需求、架构、计划和评审文档必须在开头说明适用状态。设计文档至少使用以下状态之一：

- **当前模型**：已经实现并仍适用；
- **提案**：尚未实现，不能作为操作指南；
- **历史记录**：描述指定提交或日期的旧基线。

提案命令必须明确写“当前不可执行”。历史名称和现行名称同时出现时，要说明边界。

## 4. 从需求到计划：一个特性怎么拆成文档

`requirements/`、`architecture/`、`plans/` 三个目录承载同一个特性的不同侧面。它们的界限不是主题，而是**回答的问题**和**过期方式**：

| 目录 | 回答 | 什么时候改 | 典型内容 |
| --- | --- | --- | --- |
| `requirements/` | 什么算做对了 | 目标或约束本身变化时 | 目标、范围、非目标、硬约束、验收标准、决策记录 |
| `architecture/` | 怎么做 | 设计方案改变时 | 当前模型、组件划分、机制、明确标注状态的演进方案 |
| `plans/` | 先做什么、还剩什么 | 每完成一个阶段 | 落地快照、里程碑与顺序、剩余工作、迁移步骤 |

判断一段内容归哪里，用两个测试：

- **工作量测试。** “3—5 天”“第二条 PR”只能出现在 `plans/`。它们是进度，不是约束。
- **过期测试。** 一个阶段完成后这段话是否作废？作废的进 `plans/`，不作废的进 `requirements/` 或 `architecture/`。

小特性可以只有一份文档；`requirements/` 与 `architecture/` 的界限在很多特性上是模糊的（约束与实现它的机制往往写在一起），不必为了分类硬拆。**但 `plans/` 必须独立**：它是唯一会随施工进度反复改写的部分，与稳定约束混在一份文件里，会让每次例行的状态更新都触碰安全与契约条款。

### 拆分与协作规则

1. **需求文档先写，计划文档引用它。** 计划的每个阶段用“验收：要求文档 §X、§Y”给出判定依据，**不重复叙述约束原文**。同一条约束在两处各写一遍，早晚会在只改一处时失步。
2. **计划不得定义新约束。** 如果写计划时发现某条要求在需求文档里没有，先补进需求文档，再从计划引用。
3. **里程碑名（M0、M1……）是计划词汇**，不进入需求文档。需求文档要表达顺序时，用条件而不是阶段编号：写“在实现快照写操作之前必须先决策”，不写“M4 之前”。
4. **状态只写在一处。** 已实施/未实施记录在计划文档的落地快照里；需求文档只在开头统一声明整体可执行性。
5. **阶段完成后**把稳定结论沉淀到需求、架构、开发或运维文档，并从计划的剩余工作中移除。计划全部完成后归档或删除，不留下一份看起来仍在进行的文件。

### 溯源与需求 ID

本节定义需求矩阵的**格式**。**怎么产出**这些条目——从讨论到散文、从散文抽原子断言、
如何选验证方式、需求从哪来、常见反模式——见[需求编写规范](/developer/requirement-authoring)。

一个特性跨三份文档时，靠章节号互相引用会失效——章节会重排、一节里通常有多条要求。改用稳定 ID。

**需求 ID** 是给每一条可判真假的断言分配的永久编号，格式 `<特性>-R-<三位序号>`，例如 `CONSOLE-R-042`。三条硬性质：

- **原子**：一个 ID 对应一句能判真假的话，不是一段、不是一节。背景、理由、解释不编号——全都编就变成噪音。
- **永久不变**：分配后不改，章节重排与措辞修改都不影响它。
- **不复用**：废弃的需求保留该行并标 `已废弃`，编号不再分配给别的要求。否则旧提交里引用的编号会指向另一条要求，比没有 ID 更糟。

需求文档在末尾放一张**需求矩阵**（ID、要求、验证方式），并声明：

> 本矩阵是规范来源，正文是解释。两者冲突以矩阵为准。

这样正文可以为读得顺随意改写而不动契约，也消除了「散文里哪句是硬要求」的歧义。验证方式取 `单元` / `契约` / `e2e` / `CI` / `审阅`；`审阅` 表示无法自动判定，需在 PR 中人工确认。

**溯源标注**：架构文档头部写明它满足哪些需求 ID；计划文档头部写明对应的需求与架构文档，
没有独立架构文档时也要写明这一点，免得读者去找一份不存在的文件。

计划的每个阶段**不复述要求原文**，范围用两种方式给出，各有分工：里程碑正文用章节指针提供
阅读入口（读的时候知道该翻哪里），实现检查表的归属表用需求 ID 提供精确范围（机器可校验）。
只有后者参与一致性校验。

### 实施检查表

计划文档末尾放实施检查表，**逐 PR 更新**，不是完工后一次性补写。它只记录 CI 无法自动判定的内容：

| 小节 | 内容 | 要点 |
| --- | --- | --- |
| 需求归属与覆盖 | 每个需求 ID 属于哪个里程碑、当前状态 | 每个 ID 必须**恰好**归属一个里程碑；新增需求同步补进，否则不会被任何阶段验收 |
| CI 门禁 | 每项门禁最近一次全绿的提交号 | 不逐条打勾。CI 已经门禁的事情写「哪个提交上绿」，重复打勾是表演 |
| e2e 执行记录 | 需求 ID、脚本、环境、执行日期、结果 | 只写「跑过了」三个月后无法复核，四列都要填 |
| 文档同步 | 本次变更需要同步的文档及状态 | 对应仓库对功能与文档一致性的要求 |

需求归属表与需求矩阵之间的一致性由 `npm run docs:check-requirements` 机械校验，并在文档 CI 中门禁：
矩阵里的每个未废弃 ID 必须在归属表出现且只出现一次，归属表不得引用矩阵中不存在的 ID，
标注 `e2e` 的需求必须在 e2e 记录表中有行、未标注的不得出现在那里。文档按文件名配对
（`docs/requirements/<主题>.md` 由 `docs/plans/<主题>.md` 交付）；尚未采用 ID 的需求文档会被跳过，
但已有矩阵却缺少配套计划的会报错——那意味着它的需求不会被任何阶段调度。

### 文档 frontmatter

`requirements/` 文档使用：

```yaml
---
doc_type: requirement
status: current
created: 2026-08-16
updated: 2026-08-21
---
```

`plans/` 文档在标题下用引用块声明状态、日期与目标，不使用 frontmatter：

```markdown
> 状态：**部分实施**。M0 已落地；认证、前端、任务系统尚未实现。
> 日期：2026-08-16，更新：2026-08-21
```

两者都使用稳定文件名，进度通过正文状态表达，不通过重命名表达。

## 5. 文件和结构

- 文件名使用小写 kebab-case，例如 `backup-and-restore.md`；目录入口使用 `index.md`。
- `research/` 使用稳定的主题文件名，例如 `self-hosted-git-services-research.md`，不得把创建日期、更新时间或证据截点写入文件名。研究结论更新时原地维护，不重命名页面。
- 只有事件复盘和 `reviews/` 中绑定明确时间点的历史快照使用 `YYYY-MM-DD-topic.md`；这里的日期表示事件或评审基线，而不是创建时间或最后修改时间。
- 需求、架构、计划、指南、操作、开发和参考文档都使用稳定文件名。计划状态和目标日期写在正文或 frontmatter 中，不通过改文件名表达进度。
- 每页只有一个一级标题 `#`，后续标题按层级递进，不跳级。
- 开头先说明页面解决什么问题、适合谁；任务文档优先给出结果和前置条件。
- 较长页面使用清晰的二级标题；一个段落只表达一个主要观点。
- 命令块注明语言：Shell 使用 `bash`，配置使用 `yaml`，纯输出使用 `text`，JSON 使用 `json`。
- 示例使用 `nas.example.com`、`admin@example.com`、`/srv/anas` 和 `replace-me` 等占位值，不使用真实主机或凭据。
- 第一次出现 ANAS 专有概念时使用项目统一拼写：`Module`、`Contract`、`Resource`、`Runner`、`workspace`、`deployment`。

研究文档必须在开头使用以下 frontmatter：

```yaml
---
doc_type: research
created: 2026-08-15
updated: 2026-08-20
evidence_as_of: 2026-08-19
---
```

- `created` 是文档首次创建日期，后续更新不得修改。
- `updated` 是结论、范围或重要事实最后一次实质更新日期；只调整排版或修复链接时可以不变。
- `evidence_as_of` 是动态外部事实最后一次核验日期。没有动态证据的研究可以省略，但不得用 `updated` 冒充事实截点。
- 日期统一使用 ISO `YYYY-MM-DD`。标题可在叙述确有必要时说明事实截点，但不得把日期当成页面身份。

## 6. 链接与导航

- 站内页面正文优先使用以 `/` 开头的 VitePress 路径，例如 `[备份](/guide/backup-and-restore)`；英文页面链接到 `/en/...`。
- 同一目录内的简单链接可使用相对 `.md` 路径，但一个页面内应保持一致。
- 不要链接 `docs/.vitepress/dist/`、本机绝对路径或已删除的旧目录。
- 新增可发现的页面时，同步更新 `docs/.vitepress/config/sidebar.ts`；新增一级栏目时再更新导航。
- 移动或重命名文件时，在同一提交中修复所有站内链接、README 链接和导航。
- 外部事实优先链接官方文档、规范或上游仓库，并使用可读的链接文字，不使用裸 URL 代替说明。

## 7. 命令、配置和安全

- 可复制命令必须与当前 CLI 一致，明确 `-w`、`-c` 等必要参数，并说明命令会不会修改状态。
- 危险操作必须包含前置检查、影响范围、备份要求、验证方法和恢复路径；否则不应写成 runbook。
- YAML 示例必须符合当前结构化 schema。Module 选择使用映射，不使用旧列表格式。
- 不在 `docs/` 中保存真实 Secret、IP/域名、SSH 连接方式、内部事件记录或测试服务器日志。`docs/` 中的内容默认全部公开。
- 单次验证证据放在受控 Issue、CI artifact 或外部私有系统；将稳定且已脱敏的结论整理进正式文档。

## 8. 新页面模板

```markdown
# 页面标题

一句话说明读者和目标。

> [!NOTE]
> 如果页面是提案或历史记录，在这里标明状态和基线。

## 前置条件

列出开始前必须满足的条件。

## 操作或说明

给出最短、可验证的主体内容。

## 验证

说明如何确认结果正确。

## 故障与恢复

仅在任务可能失败或修改状态时添加。

## 相关文档

链接到指南、参考或设计中的权威页面。
```

参考类页面可以用“适用范围 → 字段/命令表 → 错误与边界 → 维护来源”替代任务模板。短页面不必机械保留空章节。

## 9. 提交前检查

- [ ] 目录和目标读者正确，没有与现有页面重复。
- [ ] 研究文档使用稳定主题文件名，并正确维护 `created`、`updated` 和必要的 `evidence_as_of`。
- [ ] 用户文档已同步中英文，或按本标准说明了翻译边界。
- [ ] 自动生成的页面已在同一次生成中更新中文和英文，且两侧导航可访问。
- [ ] 命令、配置、版本和 Module 状态已对照当前实现。
- [ ] 当前实现、提案和历史记录没有混写。
- [ ] 示例不包含真实凭据、主机信息或个人数据。
- [ ] 新页面已加入侧边栏，移动页面的旧链接已修复。
- [ ] 需求或计划文档变更后，已运行 `npm run docs:check-requirements`（需求归属与 e2e 记录一致性）。
- [ ] 已运行 `npm run docs:build`，且相关代码测试通过。

文档站点的本地预览、构建和发布方式见[文档站点](documentation.md)。
