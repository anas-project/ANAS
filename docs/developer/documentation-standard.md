# 文档写作标准

本标准适用于 `docs/` 与 `dev-docs/` 中所有新增和修改内容。提交文档前，先确定读者、文档类型和事实来源，再决定目录与写法。

## 1. 先分类，再创建文件

| 目录 | 主要读者 | 内容 | 不应包含 |
| --- | --- | --- | --- |
| `getting-started/` | 第一次使用者 | 安装、前置条件、最短可用路径 | 完整参数表、内部实现 |
| `guide/` | 普通用户 | 按任务组织的配置和日常操作 | 未实现设计、调研过程 |
| `operations/` | 管理员 | 运行维护、故障处理、服务专项说明 | 开发实现细节 |
| `operations/runbooks/` | 值班管理员 | 有前置检查、风险和恢复步骤的主机操作 | 没有验证或回退的危险命令 |
| `reference/` | 用户和开发者 | 参数、Module、环境变量等可查询事实 | 推测、教程式长叙述 |
| `reference/contracts/` | 工具和集成开发者 | 稳定 CLI、JSON、文件格式契约 | 未落地的目标接口 |
| `developer/` | 贡献者 | 仓库、Module、测试、发布和文档流程 | 用户操作手册 |
| `architecture/` | 维护者 | 当前模型、设计决策和明确标注的演进方案 | 未标状态的未来命令 |
| `research/` | 决策者 | 外部事实调研、候选比较和技术选型 | 需求、实施计划、历史审查、当前操作说明 |
| `governance/` | 社区和维护者 | 项目治理、注册和政策资料 | 服务配置指南 |

一个主题可能涉及多类文档，但不要复制整段内容。用户指南说明“怎么做”，参考文档列出“有哪些”，设计文档解释“为什么”；用链接连接它们。

### 开发过程工件不在 `docs/` 下

需求、实施计划和时点评审是开发过程工件，不是给部署 ANAS 的人看的，因此不进文档站点，
放在仓库根的 `dev-docs/`，与 `contracts/`、`modules/` 平级：

| 目录 | 主要读者 | 内容 | 不应包含 |
| --- | --- | --- | --- |
| `dev-docs/requirements/` | 产品和架构维护者 | 目标、范围、硬约束和验收标准 | 候选比较、实现步骤、阶段进度 |
| `dev-docs/plans/` | 实施负责人 | 已明确目标的里程碑、迁移顺序和剩余工作 | 当前操作说明、外部候选调研 |
| `dev-docs/reviews/` | 维护者和审查者 | 绑定日期、版本或提交基线的审查与实施评估 | 持续维护的架构或操作说明 |

**归属规则**：单个 Module 私有的需求与计划放 `modules/<name>/dev-docs/`，只有 ANAS 自身或跨
Module 的才放仓库根 `dev-docs/`。判据是「这份文档描述的约束会不会在该 Module 被移除后失去意义」。
同一主题不得在两个位置同时存在，`npm run docs:check-requirements` 门禁这一条。

这三类文档**不再维护英文版**。它们是开发过程工件，读者是提交者，用中文单语维护。

`dev-docs/` 在 GitHub 上阅读，站内不渲染。因此它内部的链接一律用仓库相对路径
（`../requirements/<主题>.md`、`../../docs/architecture/<主题>.md`），不用以 `/` 开头的
VitePress 路径；反过来，`docs/` 里引用 `dev-docs/` 时用完整的仓库 URL
（`https://github.com/anas-project/ANAS/blob/master/dev-docs/...`），相对路径会让站点构建报死链。

## 2. 中英文规则

- 新增或修改面向用户的 `getting-started`、`guide`、`operations` 和核心 `reference` 页面时，必须同步维护 `/en/` 下的英文镜像。
- 中英文文件使用相同的相对路径和章节结构，便于切换与审查。
- AI Agent、生成脚本和其他自动化也必须遵守同一规则：一次任务中同时创建或更新中文页与 `docs/en/` 镜像，不能先生成单语页面并把翻译留给后续任务。
- 生成器必须把中英文文件视为同一个原子输出集合；`--check` 需要在任一文件缺失或过期时失败。新增生成页面时必须为两种语言同时添加测试和侧边栏入口。
- 中文是详细架构设计的当前源语言。暂时无法完整翻译架构或调研时，至少更新 `/en/architecture/` 或 `/en/research/` 的英文索引摘要，并明确链接到中文原文。
- `dev-docs/` 下的需求、计划与评审是开发过程工件，只维护中文，本节的双语规则不适用。
- 不要逐词硬译命令、配置键、Module 名、文件路径或错误码；这些技术标识在两种语言中保持一致。
- 两种语言必须表达相同的支持状态、风险和默认值。

## 3. 准确性与状态

按以下优先级确认事实：

1. Runner 代码、配置 schema 和测试；
2. `modules/*/module.yml`、Compose 文件和 Hook；
3. `docs/reference/contracts/` 中的稳定契约；
4. 当前指南和设计文档。

不要仅根据旧文档复制命令或默认值。提交前实际运行示例命令的 `--help`、解析或相关测试。版本、Module 状态、参数数量等容易变化的内容应注明来源或复核日期；能够链接到权威清单时，不重复维护易漂移的列表。

Module 与 Contract 的源文件、必需章节、生成标记、VitePress 镜像、双语和 CI 规则分别以 [Module 文档生成标准](/developer/module-documentation) 与 [Contract 文档生成标准](/developer/contract-documentation) 为准。生成镜像不得直接编辑；Module 的版本化时区和语言事实以 `modules/*/localization.yml` 为准。

需求、架构、计划和评审文档必须在开头说明适用状态。声明写在 frontmatter 的 `status:` 字段，
或标题下前 14 行内的 `状态：` / `Status:` 行（允许 `> **状态：…**` 这类引用块与强调写法）。
`npm run docs:check-status` 在文档 CI 中门禁这一条，覆盖 `docs/architecture/`、
`dev-docs/requirements/`、`dev-docs/plans/` 及其 Module 私有对应目录，索引页除外。

设计文档至少使用以下状态之一：

- **当前模型**：已经实现并仍适用；
- **提案**：尚未实现，不能作为操作指南；
- **历史记录**：描述指定提交或日期的旧基线。

提案命令必须明确写“当前不可执行”。历史名称和现行名称同时出现时，要说明边界。

## 4. 从需求到计划：一个特性怎么拆成文档

`dev-docs/requirements/`、`docs/architecture/`、`dev-docs/plans/` 三个目录承载同一个特性的不同侧面。它们的界限不是主题，而是**回答的问题**和**过期方式**：

| 目录 | 回答 | 什么时候改 | 典型内容 |
| --- | --- | --- | --- |
| `dev-docs/requirements/` | 什么算做对了 | 目标或约束本身变化时 | 目标、范围、非目标、硬约束、验收标准、决策记录 |
| `docs/architecture/` | 怎么做 | 设计方案改变时 | 当前模型、组件划分、机制、明确标注状态的演进方案 |
| `dev-docs/plans/` | 先做什么、还剩什么 | 每完成一个阶段 | 落地快照、里程碑与顺序、剩余工作、迁移步骤 |

判断一段内容归哪里，用两个测试：

- **工作量测试。** “3—5 天”“第二条 PR”只能出现在 `dev-docs/plans/`。它们是进度，不是约束。
- **过期测试。** 一个阶段完成后这段话是否作废？作废的进 `dev-docs/plans/`，不作废的进 `dev-docs/requirements/` 或 `docs/architecture/`。

小特性可以只有一份文档；`dev-docs/requirements/` 与 `docs/architecture/` 的界限在很多特性上是模糊的（约束与实现它的机制往往写在一起），不必为了分类硬拆。**但 `dev-docs/plans/` 必须独立**：它是唯一会随施工进度反复改写的部分，与稳定约束混在一份文件里，会让每次例行的状态更新都触碰安全与契约条款。

### 拆分与协作规则

1. **需求文档先写，计划文档引用它。** 计划的每个阶段用“验收：要求文档 §X、§Y”给出判定依据，**不重复叙述约束原文**。同一条约束在两处各写一遍，早晚会在只改一处时失步。
2. **计划不得定义新约束。** 如果写计划时发现某条要求在需求文档里没有，先补进需求文档，再从计划引用。
3. **里程碑名（M0、M1……）是计划词汇**，不进入需求文档。需求文档要表达顺序时，用条件而不是阶段编号：写“在实现快照写操作之前必须先决策”，不写“M4 之前”。
4. **状态只写在一处。** 已实施/未实施记录在计划文档的落地快照里；需求文档只在开头统一声明整体可执行性。
5. **阶段完成后**把稳定结论沉淀到需求、架构、开发或运维文档，并从计划的剩余工作中移除。计划全部完成后按下文「计划完成后归档」移入 `dev-docs/plans/archived/`，不留下一份看起来仍在进行的文件。

### 溯源与需求 ID

本节定义需求矩阵的**格式**。**怎么产出**这些条目——从讨论到散文、从散文抽原子断言、
如何选验证方式、需求从哪来、常见反模式——见[需求编写规范](/developer/requirement-authoring)。

一个特性跨三份文档时，靠章节号互相引用会失效——章节会重排、一节里通常有多条要求。改用稳定 ID。

**需求 ID** 是给每一条可判真假的断言分配的永久编号，格式 `<特性>-R-<三位序号>`，例如 `CONSOLE-R-042`。三条硬性质：

- **原子**：一个 ID 对应一句能判真假的话，不是一段、不是一节。背景、理由、解释不编号——全都编就变成噪音。
- **永久不变**：分配后不改，章节重排与措辞修改都不影响它。
- **不复用**：废弃的需求保留该行并标 `已废弃`，编号不再分配给别的要求。否则旧提交里引用的编号会指向另一条要求，比没有 ID 更糟。

需求文档在末尾放一张**需求矩阵**（ID、要求、验证方式），并声明：

> 本矩阵是规范来源，正文是解释。两者冲突以矩阵为准。

这样正文可以为读得顺随意改写而不动契约，也消除了「散文里哪句是硬要求」的歧义。验证方式取 `单元` / `契约` / `e2e` / `CI` / `审阅`；`审阅` 表示无法自动判定，需在 PR 中人工确认。

**溯源标注**：架构文档头部写明它满足哪些需求 ID；计划文档头部写明对应的需求与架构文档，
没有独立架构文档时也要写明这一点，免得读者去找一份不存在的文件。

计划的每个阶段**不复述要求原文**，范围用两种方式给出，各有分工：里程碑正文用章节指针提供
阅读入口（读的时候知道该翻哪里），实现检查表的归属表用需求 ID 提供精确范围（机器可校验）。
只有后者参与一致性校验。

### 实施检查表

计划文档末尾放实施检查表，**逐 PR 更新**，不是完工后一次性补写。它只记录 CI 无法自动判定的内容：

| 小节 | 内容 | 要点 |
| --- | --- | --- |
| 需求归属与覆盖 | 每个需求 ID 属于哪个里程碑、当前状态 | 每个 ID 必须**恰好**归属一个里程碑；新增需求同步补进，否则不会被任何阶段验收 |
| CI 门禁 | 每项门禁最近一次全绿的提交号 | 不逐条打勾。CI 已经门禁的事情写「哪个提交上绿」，重复打勾是表演 |
| e2e 执行记录 | 需求 ID、脚本、环境、执行日期、结果 | 只写「跑过了」三个月后无法复核，四列都要填 |
| 文档同步 | 本次变更需要同步的文档及状态 | 对应仓库对功能与文档一致性的要求 |

### 需求索引的状态列由机器维护

`dev-docs/requirements/index.md` 的「状态」列**不是手写的**。它由需求矩阵（全部 ID）与配套计划的里程碑
归属表（归属 + 里程碑状态）算出，用 `npm run docs:requirement-status` 生成，文档 CI 跑
`npm run docs:check-requirement-status` 门禁。手工改动会被拦下。

分工是明确的：**「文档」和「范围」两列人写，「状态」列机器写。** 新增需求文档时仍要手工补一行标题
和范围——从文件名编出来的描述比人写的差；但生成器会在发现某份需求文档在索引里没有条目时报错，
所以漏加行不会让文档在索引里静默消失。

因此里程碑表的「状态」列必须以 `已完成` / `实施中` / `未开始` / `阻塞` 之一开头，分号之后可以写
自由文本给人读（`实施中；只读部分已落地，invoke 待办` 既说明里程碑在飞，也说明落地到哪）。开头不在
词汇表内时生成器失败并指名该里程碑。

**下面这些改动之后必须重新生成**（忘了跑 CI 会拦）：

- 需求矩阵增删行，或把某行标为已退出；
- 计划的里程碑表改了状态，或改了某个里程碑的 ID 归属；
- 新增/删除一份需求文档或它的配套计划。

需求归属表与需求矩阵之间的一致性由 `npm run docs:check-requirements` 机械校验，并在文档 CI 中门禁：
矩阵里的每个未废弃 ID 必须在归属表出现且只出现一次，归属表不得引用矩阵中不存在的 ID，
标注 `e2e` 的需求必须在 e2e 记录表中有行、未标注的不得出现在那里。文档按文件名配对
（`dev-docs/requirements/<主题>.md` 由 `dev-docs/plans/<主题>.md` 交付，Module 私有主题在
`modules/<name>/dev-docs/` 下同理）；尚未采用 ID 的需求文档会被跳过，
但已有矩阵却缺少配套计划的会报错——那意味着它的需求不会被任何阶段调度。

采用机器可读测试用例的主题还必须在 `test-env/cases/<主题>/cases.yml` 中声明本轮
`requirement_scope`。用例使用稳定 `<需求前缀>-T-<三位序号>`，映射需求 ID、实现文件和可发现命令；
实现文件用 `TEST_CASES:` 注释反向声明用例 ID。同目录 README 由
`go run ./cmd/gen-test-case-docs` 生成，`npm run docs:check-requirements` 同时检查需求归属和用例 catalog。
需求文字或验证方式改变会使逐用例摘要失效，必须先复核用例和断言，再显式更新摘要。

### 文档 frontmatter

`dev-docs/requirements/` 文档使用：

```yaml
---
doc_type: requirement
status: current
created: 2026-08-16
updated: 2026-08-21
---
```

`dev-docs/plans/` 文档使用同样的 frontmatter，`status` 取值限定为四个之一：

```yaml
---
doc_type: plan
status: proposed | implementing | partial | done
created: 2026-08-16
updated: 2026-08-21
---
```

| 取值 | 含义 |
| --- | --- |
| `proposed` | 尚未开始施工 |
| `implementing` | 正在施工 |
| `partial` | 部分里程碑已落地，剩余部分未在排期 |
| `done` | 全部里程碑完成 |

`implementing` 与 `partial` 的区别是**是否还应期待进展**，不是完成了多少——完成度由需求索引从
归属表算出，不靠这个字段表达。

正文可以继续用引用块写给人读的细节（哪个里程碑落地了、基线 commit 是多少），但**机器读的唯一来源
是 frontmatter**。两处冲突时以 frontmatter 为准；`npm run docs:check-plan-status` 会拦下与之不一致
的索引状态列。

这条规则本身是被现实改过来的：早前的规则写「计划不使用 frontmatter」，而实际 18 份计划里 15 份
用了，剩下 3 份各写各的引用块格式。**状态写了七遍七种形状，没有一种机器能读**——改规则比改文档诚实。

两者都使用稳定文件名，进度通过状态字段表达，不通过重命名表达。

### 计划完成后归档

`status: done` 的计划移入 `dev-docs/plans/archived/`，**移动前先执行上面的拆分规则 5**：把稳定结论
沉淀到需求、架构、开发或运维文档，并在 `plans/index.md` 的已归档表里写明结论去向。留一份看起来仍在
进行的计划，比删掉它更糟——读者无法分辨哪些「当前」指的是历史基线。

归档的后果有两条，都是刻意的：

- **需求覆盖门禁不再校验它的归属表。** 归属表记录的是已交付的事实，不是待排的工作。门禁会把跳过的
  主题逐行列出，不是静默略过。
- **需求文档不跟着走。** 已实现的需求不会失效，它变成回归判据；把它移出视野等于让下一次改动看不见
  必须维持的约束。需求按主题分目录，不按状态分。

## 5. 文件和结构

- 文件名使用小写 kebab-case，例如 `backup-and-restore.md`；目录入口使用 `index.md`。
- `research/` 使用稳定的主题文件名，例如 `self-hosted-git-services-research.md`，不得把创建日期、更新时间或证据截点写入文件名。研究结论更新时原地维护，不重命名页面。
- 只有事件复盘和 `dev-docs/reviews/` 中绑定明确时间点的历史快照使用 `YYYY-MM-DD-topic.md`；这里的日期表示事件或评审基线，而不是创建时间或最后修改时间。
- 需求、架构、计划、指南、操作、开发和参考文档都使用稳定文件名。计划状态和目标日期写在正文或 frontmatter 中，不通过改文件名表达进度。
- 每页只有一个一级标题 `#`，后续标题按层级递进，不跳级。
- 开头先说明页面解决什么问题、适合谁；任务文档优先给出结果和前置条件。
- 较长页面使用清晰的二级标题；一个段落只表达一个主要观点。
- 命令块注明语言：Shell 使用 `bash`，配置使用 `yaml`，纯输出使用 `text`，JSON 使用 `json`。
- 示例使用 `nas.example.com`、`admin@example.com`、`/srv/anas` 和 `replace-me` 等占位值，不使用真实主机或凭据。
- 第一次出现 ANAS 专有概念时使用项目统一拼写：`Module`、`Contract`、`Resource`、`Runner`、`workspace`、`deployment`。

研究文档必须在开头使用以下 frontmatter：

```yaml
---
doc_type: research
created: 2026-08-15
updated: 2026-08-20
evidence_as_of: 2026-08-19
---
```

- `created` 是文档首次创建日期，后续更新不得修改。
- `updated` 是结论、范围或重要事实最后一次实质更新日期；只调整排版或修复链接时可以不变。
- `evidence_as_of` 是动态外部事实最后一次核验日期。没有动态证据的研究可以省略，但不得用 `updated` 冒充事实截点。
- 日期统一使用 ISO `YYYY-MM-DD`。标题可在叙述确有必要时说明事实截点，但不得把日期当成页面身份。

## 6. 链接与导航

- 站内页面正文优先使用以 `/` 开头的 VitePress 路径，例如 `[备份](/guide/backup-and-restore)`；英文页面链接到 `/en/...`。
- 同一目录内的简单链接可使用相对 `.md` 路径，但一个页面内应保持一致。
- 不要链接 `docs/.vitepress/dist/`、本机绝对路径或已删除的旧目录。
- `docs/` 引用 `dev-docs/` 时使用完整仓库 URL；`dev-docs/` 内部一律用仓库相对路径。
- **`docs/` 引用 `dev-docs/` 的结论时，把结论写进本页，链接只作为出处保留。** 站点页面必须自足：
  读者不该为了看懂一段规则而离开站点去翻一份不发布的开发工件。写法是先陈述结论，再用一句
  「规范来源是 X，冲突以它的需求矩阵为准」收尾，而不是用「详见 X」代替结论本身。摘要与来源冲突
  时以来源为准，所以摘要要写判据和边界，不要复制整段原文——复制会带来第二份需要同步的正文。
- 新增可发现的页面时，同步更新 `docs/.vitepress/config/sidebar.ts`；新增一级栏目时再更新导航。
- 移动或重命名文件时，在同一提交中修复所有站内链接、README 链接和导航。
- 外部事实优先链接官方文档、规范或上游仓库，并使用可读的链接文字，不使用裸 URL 代替说明。

## 7. 命令、配置和安全

- 可复制命令必须与当前 CLI 一致，明确 `-w`、`-c` 等必要参数，并说明命令会不会修改状态。
- 危险操作必须包含前置检查、影响范围、备份要求、验证方法和恢复路径；否则不应写成 runbook。
- YAML 示例必须符合当前结构化 schema。Module 选择使用映射，不使用旧列表格式。
- 不在 `docs/` 中保存真实 Secret、IP/域名、SSH 连接方式、内部事件记录或测试服务器日志。`docs/` 中的内容默认全部公开。
- 单次验证证据放在受控 Issue、CI artifact 或外部私有系统；将稳定且已脱敏的结论整理进正式文档。
