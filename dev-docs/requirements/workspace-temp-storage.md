# Workspace 临时存储要求

本文规定 Module 临时存储范围与回归验收标准；实现与验收绑定配套计划中的冻结候选，本次文档提交不包含产品实现。验收执行结果、各自源码/制品基线和历史失败统一记录在[归档实施计划](../plans/archived/workspace-temp-storage.md)，不由某一历史基线的通过推断其他源码或部署通过。

## 1. 背景与范围

2026-09-30 的 [Collabora 诊断](../reviews/2026-09-30-collabora-disk-pressure.md)确认：根分区仅余 2.1 GB，文档临时目录位于 Docker overlay，文档打开报 Disk-Full，但容器健康检查通过。本要求解决这类 Module 专用临时目录的存放与切换问题。

范围以 **Module 显式声明的临时目录** 为准：Module 声明目录可在容器停止并解除引用后丢弃，Runner 为其分配宿主目录并挂载到声明的位置。Collabora 的文档临时树是首个验收场景。不能仅凭目录名、文件年龄或“位于系统临时目录之外”推断可删除性；Module 的 `/tmp` 如需纳管，也采用同一显式声明机制。未声明的容器目录保持原有行为。

本功能不统一 Runner、Hook 构建或配置校验的系统临时文件，不设置失败 job 的 24 小时保留策略，不接入远程测试产物管理。长期缓存、测试报告、镜像回滚材料和业务数据也不在自动清理范围。原子替换文件继续在目标文件旁创建中间文件。首版不要求硬配额或常驻 GC 服务。

本次范围与责任划分来自[设计讨论的保留结论](../plans/archived/workspace-temp-storage.md#历史设计与停止审阅的结论)。现有执行顺序和锁作为复用基线，具体调用位置与剩余验收工作见配套计划。

## 2. 路径与所有权

默认根为 `<workspace>/tmp`；`global.temp_path` 接受显式绝对路径，允许初始化后修改。Module 声明目录名称、容器内挂载目标、容器生命周期、UID/GID 与权限、空间下限和必要的文件系统条件。声明格式需能表达 Collabora 目标镜像的目录约束，不要求所有 Module 使用相同的容器内路径。

外部根下按稳定 workspace 身份隔离，再按 Module、容器实例与声明名称分配目录。Module 只获得自身声明的挂载。登记、租约与历史路径放在 workspace 的 `.anas/temp/`，目录内同时带可核验的所有权标记；这里的租约是记录“哪个容器仍占用哪个目录”，不引入 Runner job 调度或独立服务。克隆工作区须建立新的临时所有权身份，不能控制源工作区目录。

外部存储首次登记其文件系统身份，后续分配与挂载前复核；磁盘未挂载时同名空目录不能成为替代位置。业务目录和未登记文件不能被纳入清理。普通目录不承诺硬容量上限。

## 3. 初始化后修改路径

**不复制临时内容；通过所有 Module 的停止、切换与重新启动统一应用新路径。** 这是 2026-09-30 操作者明确的产品行为，替代先前“仅后续实例切换、旧实例长期排空”的提案。

### 3.1 执行顺序与停止责任

修改解析后的临时根时，Runner 复用现有 workspace 排他锁，在锁内核对配置与当前 deployment、验证目标路径/权限/文件系统/容量并准备新的 deployment，然后执行切换。临时目录分配、切换和回收与现有生命周期操作共用锁边界，切换期间不能并发启动使用旧目录的新实例；不另建执行锁、调度器或等待所有 Runner job 的排空流程。

按旧 deployment 的依赖逆序停止全部 Module，确认容器及挂载引用已释放，再在新路径分配临时树，按目标 deployment 的依赖正序启动全部已启用 Module。包括未声明临时目录的 Module，不能仅重启 Collabora。容器挂载源变化时采用重建，普通 Docker restart 不能应用新挂载。仅文本变化但解析为相同根时，不因临时路径配置额外触发全量重启。

正常停止时的数据保存由容器内应用负责，Module 负责正确传递停止信号和配置适当的停止等待时间。Core 复用现有正常停止入口及已有 Module 钩子，不新增应用保存确认、WOPI 调用或编辑会话管理流程。停止入口返回错误、超时或无法证明引用已释放时，中止切换，不强删目录。切换计划仍需展示全部重启范围和编辑会话中断影响。

### 3.2 切换成功与失败处理

切换沿用现有 Module 启动链路及其失败语义。全部目标 Module 的启动链路成功返回，并确认新容器声明的临时挂载实际指向本次登记的目录后，提交已应用状态，清理旧路径中本 workspace 已释放的受管临时内容。共享根中其他 workspace 与未受管文件继续保留。

**应用全面可用不是本功能新增的切换门槛。** 在已有启动链路成功且存储检查通过的前提下，应用仍在初始化或存在与存储无关的健康问题，不应额外阻止切换或触发回滚。容器创建/启动失败、现有启动钩子失败和临时挂载错误仍按失败处理。真实文档打开、编辑和保存用于 Collabora 接入的 E2E 验收，不要求每次切换都执行一遍。

目标预检失败不得停止现有服务。停止、启动或存储核验失败时，停止已启动的新实例并尝试恢复旧 deployment 与旧路径；保留尚未清理的旧内容，分别报告首因与恢复结果。新路径应用成功但旧目录清理失败时保留新路径运行，报告“已切换、清理未完成”，保留可重试登记，不回滚已成功切换的服务。清理可能部分完成，因此需要记录阶段供中断后恢复。

## 4. 历史回滚与恢复

**历史回滚复用修改配置时的临时路径切换策略，不另建回滚专用策略。** 将历史目标配置中的 temp_path 与当前已应用路径比较；解析后不同，就依据历史目标配置准备新的目标 deployment，执行 §3 的同一预检、全量停启、重新分配和清理流程，不改写历史不可变 deployment。

历史临时内容不复制、不恢复，已释放的历史租约不重新启用。旧盘缺失等情况沿用目标预检失败语义。解析后路径相同，不因本功能增加一次全量切换；原有版本、其他配置或业务数据的回滚规则继续适用。

受管临时内容不进入备份或快照，恢复后重新分配。配置中的外部路径可以保留为 desired state，但目标宿主必须重新验证；不能沿用源 workspace 的租约挂载或清理源实例目录。恢复后的不可变制品通过本 workspace 的新目录分配结果启动，不能直接把制品中遗留的实例路径当成有效租约。

## 5. 生命周期与存储状态

容器目录在运行期间只由应用管理内容，GC 不按 mtime 删除。目录回收前核验登记、实际 Docker 容器和挂载引用；容器仅停止或进程消失不代表其引用已经解除。异常退出后重新对账，无法确认所有权或释放状态时保留并报告原因。此规则只覆盖 Module 受管目录，不附带 job 成功/失败的保留期。

分配前检查实际文件系统的可用字节和 inode；运行检查显示存储问题，不能用进程探针成功掩盖已发现的空间故障，也不能通过不断重启恢复。运行问题可与[运行问题记录要求](runtime-issues.md)共用展示机制；存储预检不能依赖其全部交付。

CLI 提供 `anas temp status`、`anas temp gc --dry-run` 和 `anas temp gc`。状态及清理只面向当前根、历史根中已登记的 Module 目录，输出归属、占用、使用状态和回收阻碍，不暴露临时文件内容。

Docker 查询、停启和补偿复用[Compose 执行边界要求](compose-execution-boundary.md)规定的同一次命令 endpoint 绑定。无法确认实际 Docker 使用者的目录按未知状态保留，不能把查询错误当作“无人使用”。

本次不改变 Docker 初始化或 CLI 连接选择契约；init 持久绑定程序及连接的候选方案记录在配套计划的待决策项中，不作为已确定要求。
