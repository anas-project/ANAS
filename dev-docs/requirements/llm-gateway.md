# LLM Gateway 要求（待讨论）

> 状态：**待讨论**。本文只锁定问题域与边界，**尚未形成需求矩阵**，因此不参与
> `npm run docs:check-requirements` 的归属校验，也没有配套实施计划。讨论收敛后再补矩阵与计划。

## 1. 为什么需要

[AI Agent 编排](../../modules/ai_agent/dev-docs/requirements/ai-agent.md)把模型访问凭据当作运行时
注册表里的一项（`auth_mode` / `credential_id`），执行实例在作业期直接持有它。这条路能跑通，但留下
四个问题没人负责：

1. **凭据集中度**：每个运行时一份长期厂商凭据，散在 Secret Store 里，撤销要逐个改；
2. **预算的执行点**：预算上限目前由编排器自己核算并中断，属于"自己管自己"，模型侧没有硬闸；
3. **用量归因**：token 与花费来自各家 `usage` 事件，格式不同、口径不同，跨运行时对账靠适配器自证；
4. **审计**：谁在什么时候用哪个模型问了什么，只有编排器一份记录，没有独立于调用方的第二份证据。

一个统一的模型访问网关可以把这四件事收到一处：对内发**每消费者/每作业的虚拟 key**，对外持有真实
厂商凭据；预算与限流在网关强制；用量与审计由网关记账。

## 2. 待讨论的问题

| # | 问题 | 备选 |
| --- | --- | --- |
| 1 | 自研还是引入上游 | 引入成熟开源网关（需要单独的[选型调研](../../docs/research/)）；或只做一层最小代理 |
| 2 | 形态 | 独立 ANAS Module（`llm_gateway`）+ 新 Capability/Contract；或作为 `ai_agent` 内的一个组件 |
| 3 | 接口 | 是否暴露 OpenAI 兼容 API 面；消费者是否需要感知 provider 差异 |
| 4 | 虚拟 key 粒度 | 每 Agent / 每仓库 / 每作业；作业级最利于撤销与归因，代价是签发频率 |
| 5 | 预算语义 | 硬闸（超限拒绝请求）还是软闸（超限告警由调用方中断）；与 `AGENT-R-058` 的关系 |
| 6 | 订阅登录类凭据 | Codex/Claude Code 的订阅会话不是 API key，网关代理不了；这类是否只能绕过网关直连，从而形成两套路径 |
| 7 | 出网边界 | 网关是否成为唯一出网点；执行实例的 allowlist 能否因此收敛到只剩网关与 Forgejo |
| 8 | 审计与保留 | 是否记录 prompt 与响应正文（隐私与体积）；保留期与脱敏口径 |
| 9 | 可用性 | 网关故障时 Agent 是降级直连还是整体停摆 |
| 10 | 与既有能力的关系 | 是否需要新的 Contract，还是复用现有 Capability 模式 |

## 3. 暂定边界（讨论前的默认立场，可推翻）

- 网关**不承担**模型选择与提示工程，只做凭据、预算、限流、记账与审计；
- 不引入对某一家厂商的强绑定；接入新 provider 不改消费者；
- 不成为单点：`ai_agent` 必须能在网关未部署时按现状运行（直连 + 编排器自核算），网关是增强而非前置；
- 不保存 prompt 正文，除非讨论中明确决定并给出保留期与脱敏口径。

## 4. 与 `ai_agent` 的交界

采纳后需要修改的既有约定（现在只登记，不实施）：

| 既有条目 | 可能的变化 |
| --- | --- |
| `AGENT-R-058`（预算与墙钟硬上限） | 预算的执行点从编排器移到网关，编排器保留墙钟 |
| 运行时注册表的 `auth_mode` / `credential_id` | 增加"经网关"的第三种形态 |
| 执行实例的出网 allowlist（`AGENT-R-042`） | 模型域名收敛为网关地址 |
| 记录与用量（`AGENT-R-052`） | 以网关计费为准，编排器记录降级为交叉核对 |
