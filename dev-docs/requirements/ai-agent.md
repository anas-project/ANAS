# AI Agent 编排集成要求

本文规定 ANAS 交付 `ai_agent` Module 时必须达到的用户结果、边界、安全约束与验收标准。设计方案见
[AI Agent 编排设计](../../docs/architecture/ai-agent-orchestration-design.md)，施工顺序与进度见
[AI Agent 编排实施计划](../plans/ai-agent.md)。协作面固定为已集成的 `forgejo` Module，执行面依赖
[Incus compute Provider 要求](incus-module.md)。本文不重复设计推导，也不把实现进度当作需求。

关键词“必须”“不得”“应该”具有规范性。

## 1. 目标

ANAS 必须提供可独立部署的 `ai_agent` Module，使团队能在 Forgejo 的 issue 中与 AI Agent 讨论需求、
形成入库文档，并在获得显式批准后由 Agent 在隔离实例中修改代码、运行测试并提交 PR，全过程可授权、
可审计、可中断、可核算成本。

首期目标是**单租户、成员可信**部署下的可用闭环，不以多租户隔离、对抗式威胁模型或自动合并为前置。

## 2. 范围

首期必须包含：

- `ai_agent` Module：manifest、Hook、控制面服务、数据库 Resource、双语文档与单元测试；
- Agent 身份与凭据的无人值守发放与轮换；
- Forgejo webhook 入站、去重、对账与自触发过滤；
- issue 表单模板生成与解析、标签与命令控制面、状态评论与反应；
- 文档产出入库（由控制面提交）与执行依据冻结；
- 三层权限判定、目录组授权与即时否决；
- 按仓库切分的工作实例、分支与 PR 策略、执行 issue 与队列顺序；
- 排程（截止、预估、时机与事件触发）与预算上限；
- 记录、用量核算、会话视图与终端附着。

首期不要求：

- Forgejo Projects 看板的读写（上游无 API）；
- 外部代码托管（GitHub 等）与非 Forgejo 协作面；
- 以 Forgejo Actions 作为执行后端；
- 自动合并 PR 或自动批准高风险变更；
- 多租户与对抗式威胁模型下的强制隔离。

## 3. Module 与部署边界

1. Module 名必须为 `ai_agent`，类别为 `app`；真实部署验收完成前状态必须为 `developing`。编排器作为
   独立上游项目打包，镜像 tag 必须固定，不得使用 `latest`。
2. 控制面容器不得获得宿主 Docker socket、宿主目录挂载或特权，也不得在 ANAS 核心宿主执行模型生成
   的代码。
3. Module 必须消费 `relational_database`（默认 PostgreSQL）保存编排状态；进程内不得保存权威状态，
   重启后必须能仅凭数据库与持久卷继续。
4. `enabled` 必须是唯一功能开关。缺少 Forgejo 管理凭据、仓库白名单、Agent 运行时镜像或 `compute`
   绑定时，Hook 必须拒绝开启，不得形成半功能状态。

## 4. 身份与凭据

1. 每个 Agent 必须拥有独立 Forgejo 账号（`agent-<id>`），由管理端 API 无人值守创建，且不得用于
   交互登录。
2. Agent token 必须同时限定 scope 与目标仓库，写权限只在执行阶段追加。固定版本不支持按仓库限定时，
   必须退化为“每 Agent 每仓库独立账号”并在文档中记录该退化。
3. token 与 SSH key 的轮换必须可无人工完成，失败时不得留下双活凭据。
4. Forgejo 管理凭据只能用于建账号、发凭据、注册 webhook、维护标签与模板；不得进入工作实例，必须
   单独审计与轮换。
5. webhook secret 必须由 ANAS 生成并纳入统一凭据轮换；轮换必须同时重新登记 webhook。
6. 任何凭据不得写入 issue、评论、日志、镜像或 deployment manifest。

## 5. 事件入站

1. ingress 必须校验 `X-Forgejo-Signature` 与仓库白名单，先持久化到 inbox 再返回 `202`；业务处理不得
   发生在请求路径内。
2. 同一事件重复投递必须只产生一次外部副作用。
3. 必须实现周期对账补回丢失事件，且对账不得产生重复副作用。
4. 必须忽略 Agent 账号自身产生的事件，并用 outbox 标识二次去重，杜绝自触发循环。

## 6. 交互契约

1. issue 表单模板必须由 Agent 注册表生成并提交到默认分支；注册表变化必须触发重新生成；模板内容不得
   硬编码运行时名称。
2. 表单答案解析必须容错（字段缺失、顺序变化、正文被人工编辑）；无法解析时必须降级为默认配置并说明。
3. 越权或非法的 Agent、模型、思考强度、预算档与完成方式必须降级到允许集合，并逐条说明降级原因。
4. Agent 的指派必须由编排器在 issue 创建后通过 API 完成。
5. 每个 issue 必须只有一条 Agent 状态评论并原地更新；对话内容必须新建评论；纯确认必须使用 reaction，
   不得发占位评论。
6. 模型与思考强度不得写入标签；标签只承载授权与流程控制。
7. 同一 issue 的回合必须串行；生成期间到达的新评论必须排队并可被中断命令打断。
8. 多 Agent 圆桌必须由唯一主持发起，并受轮数、预算、墙钟与无回应超时的硬上限约束；因上限终止必须
   在产出中标注。
9. 评论命令与标签必须语义等价、经过同一授权判定，且命令执行后写回对应标签。

## 7. 产物与执行依据

1. 文档必须由控制面提交（Forgejo contents API）；讨论与计划阶段的 Agent 工作区不得持有 git 写凭据。
2. 文档路径必须落在该仓库配置允许的目录内，越权路径必须拒绝。
3. 评论中引用产物必须使用指向具体 commit 的永久链接。
4. 引导流程必须能在不克隆仓库的前提下产出 `.anas-agent.yml` 并开 PR。
5. 执行依据必须是批准时冻结的 `(文档路径, commit SHA)`；任一变化必须使既有批准失效。
6. 调研类产出必须遵循目标仓库既有的研究文档规范。

## 8. 权限

1. 未启用 Agent 的仓库事件必须直接丢弃。
2. 默认动作集必须由 Forgejo 仓库权限推导（read→`reply`；write→`reply`+`plan`；maintain/admin→追加
   `execute`），且必须支持逐条覆盖与整体关闭同步。
3. 部署级使用权必须来自目录组（`CAP_ai_agent_*`）经 IAM 与 Forgejo team 的投影；最终动作集必须是
   目录组上限、仓库推导与覆盖条目的交集。
4. 必须提供优先于一切推导的即时否决表，命令执行后立即生效。
5. 每次判定（含拒绝）必须写入审计记录，含主体、来源、动作、判定依据与时间。
6. 作业真正开始前必须重新判定一次。
7. issue 正文、模板答案与评论中的配置只能收窄授权，不得放宽。

## 9. 执行面

1. 工作实例必须按仓库切分，跨仓库不得共用；必须支持“每作业一次性实例”的更强档位。
2. 每个 issue 必须有独立 worktree、独立会话目录与独立工作分支。
3. 执行凭据只能在作业期注入实例内存文件系统，作业结束必须吊销；不得写入镜像、环境变量或日志。
4. 默认必须新建 `ai/<issue>-<version>` 分支并开 PR；受保护分支永不直推；直接提交必须同时满足仓库
   策略开启与目标分支未受保护。
5. 批准后必须默认另开执行 issue，与父 issue 建立依赖与交叉引用，结束时回写摘要并解除阻塞；必须
   支持按仓库或按 issue 关闭拆分。
6. 出网必须默认拒绝，仅放行显式 allowlist。
7. 取消必须中断 Agent、销毁实例并使状态最终一致。
8. 重复触发不得产生重复 PR、commit 或评论；所有外部写操作必须带幂等键。

## 10. 排程

1. 预估必须由 Agent 在执行前给出并记录，不得要求用户填写。
2. 入队必须校验预计完成时间不晚于 `due_date`；不满足必须标记风险并说明差额，不得静默超时执行。
3. 队列顺序必须只由 issue 依赖、截止时间与优先级/入队时间决定。
4. 必须支持立即、定时、事件与暂停四种执行时机；事件等待必须有超时并回落人工批准。
5. 必须支持串行与并行并发配置，并受主机资源门槛约束。
6. 实际耗时必须写回 Forgejo 原生工时记录。
7. 队列顺序必须对人可见；置顶不可用时必须降级并说明。

## 11. 记录、用量与视图

1. 必须记录事件、每轮模型交互（含 token 与花费）、作业、判定、产物与每日汇总。
2. 上下文组装必须按来源记录剔除该 Agent 自身的历史评论、保留其他 Agent 发言并标注身份；会话重建时
   必须补回其自身发言。
3. 会话状态必须保存在持久卷；容器重建后必须能续接；续接失败必须降级为从文档、时间线与状态评论重建
   上下文。
4. 中间执行步骤不得逐条发评论；进度只更新状态评论且必须节流。
5. 记录写入前必须脱敏；大产物只存 URI 与摘要；保留期必须分层可配置。
6. 终端附着：管理员组成员默认可用，非管理员必须显式获得终端能力组；默认只读，输入必须要求 `execute`
   级授权并记为归属到该人的交互记录。
7. 预算与墙钟上限必须硬性生效，超限必须中断并回写说明。

## 12. 可扩展性

1. 新增 Agent 运行时只应需要：实现适配器、在注册表登记、提供固定 fingerprint 镜像。标签、模板、
   能力组与命令必须由注册表生成。
2. 控制面代码不得按运行时名称分支；运行时差异只能存在于适配器与注册表。
3. 思考强度必须使用运行时原生取值；非法取值必须拒绝并给出可选项。

## 13. 验收标准

### 13.1 静态与单元验收

- manifest、Compose、Hook 与双语文档通过仓库全部 manifest/documentation gate；
- 单元测试覆盖：验签与去重、模板生成与解析容错、降级说明、判定矩阵（含拒绝）、路径白名单、幂等键、
  注册表驱动的无硬编码、思考强度校验、节流与串行回合；
- 契约测试覆盖 Forgejo API 调用面与 `compute` 操作面的请求/结果形状。

### 13.2 真实部署验收

- 在固定 `forgejo 15.0.7` 与真实 Incus 宿主上完成端到端：讨论 → 文档入库 → 批准 → 执行 issue →
  分支 → PR；
- 验证凭据引导与轮换、目录组授权与即时否决、跨仓库实例隔离、出网 allowlist、取消与幂等、会话续接
  与降级、预算与墙钟截断、工时回写、终端附着授权；
- 记录控制面常驻资源、单作业资源与一次典型作业的墙钟与花费。

完成 §13.1 只代表实现进入 `developing`；只有 §13.2 全部有可复现证据才可提升为 `release`。
