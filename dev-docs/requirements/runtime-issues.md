# 运行问题记录要求

本文规定 ANAS 如何记录并展示「现在哪里不对」。配套计划见[运行问题记录实施计划](../plans/runtime-issues.md)。

关键词“必须”“不得”“应该”具有规范性。ID 一经分配即固定，废弃的需求保留行并标 `已废弃`。

## 1. 为什么需要它

有些错误不是在某次命令里当场发生的，而是之后在运行中出现：宿主重启时端口被别的服务抢先占用、之后有人用 Docker
发布了同一个端口、规则被人改动。此时没有一个正在执行的命令可以报错；只写日志，又得有人去翻才知道。首个使用者是
Incus 端口绑定（`INCUS-R-154`、`R-161`、`R-162`）。

日志回答「发生过什么」，运行问题回答「现在哪里不对」：同一个问题反复出现只算一条，条件恢复后标记为已解决。两者
分开记录，用同一个键互相对应。

## 2. 范围

必须包含：记录格式与去重、写入方与存放位置、CLI 与控制台查看、敏感值边界。

不要求：告警推送（邮件、Webhook）；日志的存放与保留期，那归[日志与可观测性](../../docs/architecture/observability-and-logs.md)；
job 事件。

## 3. 设计要点

- 每条记录有一个固定键（例如 `incus.port-binding/<租约>/tcp/2222`），另有来源（CLI apply、anasd、hostd、开机恢复）、
  级别（错误、警告）、说明、首次与最近发现时间和次数。已解决的记录带解决时间，保留一段时间供回看。
- Core 与 anasd 发现的问题写进工作区状态目录，hostd 发现的宿主级问题写进宿主状态目录，各自用文件锁原子更新。
  任一写入方不在，其余照常工作。
- 查看：CLI 命令直接读这些文件，anasd 不在也能用；控制台经 API 读同一份数据。
- Module 在 ANAS 的信任边界之外，不直接写入；它们的错误由 Module 自己的日志与健康检查表达。

## 4. 需求矩阵

| ID | 要求 | 验证方式 |
| --- | --- | --- |
| `ISSUE-R-001` | 运行问题必须作为当前状态记录，与日志分开：每条记录包含固定键、来源、级别、说明、首次与最近发现时间和次数，已解决的记录包含解决时间 | 契约 |
| `ISSUE-R-002` | 同一个键再次被发现时，只能更新最近发现时间与次数，不得新增记录；条件恢复后必须标为已解决；已解决记录保留一段时间后清除 | 单元 |
| `ISSUE-R-003` | 记录不得包含凭据、私钥或其他敏感值 | 单元 |
| `ISSUE-R-004` | CLI 的 apply、anasd 与 hostd 都必须能写入各自发现的问题；写入必须原子，任一写入方不在时其余照常工作 | 单元 |
| `ISSUE-R-005` | 每次新增或解决一条问题，都必须写一条带同一个键的日志 | 单元 |
| `ISSUE-R-006` | CLI 必须提供查看命令：直接读取记录，不依赖 anasd 在运行；支持 `--json`；存在未解决的错误级问题时退出码非零 | 契约 + e2e |
| `ISSUE-R-007` | 控制台必须经 API 显示同一份记录，不得另存一份 | 契约 |
| `ISSUE-R-008` | 记录无法读取时，查看方必须报告读取失败，不得显示为没有问题 | 单元 |
| `ISSUE-R-009` | Module 不得直接写入运行问题记录 | 审阅 |
