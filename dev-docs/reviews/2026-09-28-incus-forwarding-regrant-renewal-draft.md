2026-09-28 操作者决定：先确定是否采用期限续期方案（对比文档 §9 另有事件驱动的候选 D），再决定是否采纳本草案。
规则一在两种方案下都需要。规则二只适用于续期方案；如果采用 D，它的逐实例语义改为按事件增量处理，草案 B6
（owner 失联后许可在一个期限内失效）不再适用。

## 1. 为什么需要这两条规则

以下是已对照代码核实的现状：

- 许可是逐实例、带 30 秒期限的内核元素。每次续期都要按 `INCUS-R-102` 重新核验实例身份。
- `ForwardingLeaseGrant` 把两类东西放在一起：操作者批准的内容，和 hostd 观察到的事实。任何一项事实变化都会
  `ErrDrift`；同一 scope 不能换 grant 再 enable；`failed`、`released` 状态的 scope 也不能再 enable
  （`internal/incusprovision/forwarding_permissions.go`）。
- anasd 在领取每个工作区写任务之前，会先用 `incus.forwarding.withdraw` 关闭该工作区的全部转发，这个动作只关不开
  （`internal/jobexecutor/workspace_ingress_change.go`）。
- 实例集合一旦变化，Refresh 就整体 Close，撤销全部实例的连接（`internal/incusingresshost/forwarding_kernel.go`）。

结果是：部署一次或宿主重启一次之后，转发就一直关着，没有合法路径重新打开；one-job 实例每增减一次，同租约里
其他作业的连接都会被切断。

## 2. 规则一：确认批准的是什么，什么时候可以不经人工重新打开

### 2.1 决定

grant 的字段分成两类：

| 类别 | 字段 | 处理 |
| --- | --- | --- |
| 授权要素 | 工作区；消费者与资源（租约身份）；本机受管 Incus 归属（ownership ID）；目的 IPv4/TCP 集合；实例上限 | 由一次性确认批准 |
| 绑定事实 | 部署 ID 与 epoch、工作区摘要、bundle 摘要、Incus 版本、租约 project/接口/实例前缀、投递证书指纹、bridge 身份（boot ID、名称、MAC、ifindex、网段）、路由（出口接口、源地址、网关、路由表） | 每次续期或重新打开都由 hostd 重新观察，不需要人确认 |

- 绑定事实变了而授权要素没变，运行 owner 自动发起重新打开：hostd 重新完成全部核验，以新 generation 生效，
  旧 generation 的回执和失败历史保留（`INCUS-R-104`）。
- 授权要素扩大，必须重新 plan 并确认；缩小则自动生效。
- 时机：工作区写任务到达终态、补偿确认之后，按当时的活动部署核验。任务执行中、恢复中或补偿未确认时保持关闭。
- 不自动重新打开的情况：活动部署不再声明该租约、租约已撤销（`INCUS-R-111`）、记录处于 `pending`/`failed`
  且未恢复、操作者已 disable 或 retire。
- 触发自动重新打开的事件包括：新部署激活、宿主重启、Incus 升级、租约证书轮换、路由或接口编号变化。

### 2.2 否决的方案

- **每次都要人工确认**：任何一个 Module 部署一次、宿主重启一次，Forgejo runner 就断网，直到有人批准。频繁出现的
  确认会被当成例行点击，确认就失去了意义。
- **用部署确认代替宿主确认**（把目的地写进租约声明，随 apply 冻结）：能自然跨越 epoch，但要改 compute Contract，
  而且宿主效果的批准会从「由执行者自己给出摘要」退回到部署计划。可以作为后续演进，不在本轮。
- **失效后不再恢复**（现状）：同一个租约的转发实际上只能用一次。

### 2.3 断言（拟）

| 拟编号 | 要求 | 验证 |
| --- | --- | --- |
| 草案 A1 | 转发确认只批准授权要素（工作区、消费者与资源、本机受管 Incus 归属、目的 IPv4/TCP 集合、实例上限）；hostd 不得把部署 epoch、证书指纹、bundle、Incus 版本、boot ID、接口编号或路由当作已批准内容沿用，每次续期或重新打开都必须重新观察 | 单元 |
| 草案 A2 | 绑定事实变化而授权要素不变时，运行 owner 必须能不经人工确认发起重新打开；hostd 必须重新完成 `INCUS-R-101`/`R-102` 的全部核验后以新 generation 生效，并保留旧 generation 的回执与失败历史 | 单元 + e2e |
| 草案 A3 | 授权要素的任何扩大（新增目的地、提高实例上限、改变租约身份或 Incus 归属）必须重新 plan 并一次性确认 | 单元 |
| 草案 A4 | 授权要素缩小（移除目的地、降低实例上限）必须在下一次续期或重新打开时生效，被移除目的地的许可与连接必须撤销 | 单元 + e2e |
| 草案 A5 | 由工作区写任务触发的重新打开，只能在该任务到达终态且没有待确认补偿之后，按当时的活动部署发起；任务执行、恢复或补偿未确认期间转发必须保持关闭 | 单元 |
| 草案 A6 | 活动部署不再声明该租约、租约已撤销，或授权记录处于 `pending`/`failed` 未恢复状态时，不得自动重新打开 | 单元 + e2e |
| 草案 A7 | 自动续期与重新打开只能作用于状态为 `enabled`、且 generation 与调度时一致的授权；操作者 disable 或 retire 之后到达的续期或重新打开不得恢复放行 | 单元 |
| 草案 A8 | 每次自动重新打开都必须写宿主审计，包含原 generation、新 generation、触发原因与核验结果 | 单元 |

## 3. 规则二：增量续期

前提是保留「期限 + 续期」模型，即运行 owner 采用 B1 或 A。如果改为 C2（bridge 级、无期限许可），本节不适用，
需要另写需求。

### 3.1 决定

每次续期按实例分别处理：

- 身份不变的实例（UUID、运行代际、地址、MAC、宿主 veth 与对端编号都相同）：只延长期限；
- 新出现的实例：核验通过才加入；某个实例核验失败，只排除这一个；
- 离开或身份变化的实例：撤销它的许可，只精确清理它自己的连接；清理未确认时保留待清理记录；
- 租约级核验失败（活动部署、投递凭据、bundle、bridge、路由）：整个 scope 本次不续，让许可按期限失效，
  不沿用上一次的观察结果。

内核修改要原子生效。owner 正常时，长连接跨越多轮续期不断；owner 失联时，许可在一个期限内失效。

### 3.2 否决的方案

- **整体替换**（现状）：实例每增减一次，就断开同租约里所有作业的连接。
- **任一实例核验失败就整个 scope 不续**：一个坏实例会让整个租约断网。租约级事实失败时仍然整体不续。

### 3.3 断言（拟）

| 拟编号 | 要求 | 验证 |
| --- | --- | --- |
| 草案 B1 | 续期时身份未变的实例（UUID、运行代际、地址、MAC、宿主 veth 与对端编号均相同）只能延长许可期限，不得关闭其许可或清理其连接；已建立的 TCP 连接必须跨越多次续期保持不断 | 单元 + e2e |
| 草案 B2 | 新出现的实例必须先通过 `INCUS-R-102` 核验才加入许可；单个实例核验失败只排除该实例，不得影响其他实例续期 | 单元 |
| 草案 B3 | 离开或身份改变的实例必须在下一次续期中撤销许可，且只精确清理该实例的既有连接；清理未确认时必须保留该实例的待清理记录 | 单元 + e2e |
| 草案 B4 | 租约级核验（活动部署仍声明租约、投递凭据、bundle、bridge 与路由）失败时，整个 scope 本次不得续期，也不得沿用上一次的观察结果 | 单元 |
| 草案 B5 | 续期对内核许可的修改必须原子生效：修改过程中，身份未变实例的放行不得出现间断 | 单元 + e2e |
| 草案 B6 | 运行 owner 停止或失联后，许可必须在不超过一个期限的时间内停止放行新连接 | e2e |

## 4. 采纳时要做的事

1. 正文：在 Incus 要求中新增「转发许可生命周期」一节，写入本文 §2.1、§3.1 的决定和 §2.2、§3.2 的否决理由。
2. 矩阵：从 `INCUS-R-112` 起按顺序分配编号，归 M10a；同步更新计划 M10a 的需求范围，运行
   `docs:check-requirements`、`docs:requirement-status`、`docs:plan-status`。
3. 宿主通道：草案 A2、A7 引入「不经人工确认、由既有确认派生的变更动作」。现有无确认的先例只有只读观察和只关不开
   的 withdraw，需要在宿主通道要求中补一条派生授权的边界：只能在原批准范围内、不得扩大、每次重新观察。
4. 实现侧：去掉「同 scope 不能换 grant」「`failed`/`released` 不能再 enable」两处限制，改为按 generation 续接；
   Refresh 改为增量语义。

## 5. 待确认的问题

1. 提高实例上限是否算扩大、需要重新确认？草案认为算。
2. 宿主重启后的恢复是否也走草案 A2 自动重新打开？草案认为走。
3. 目的地 IP 随部署变化（例如被访问的服务换了地址）时，是否算授权要素变化？草案认为算，需要重新确认。
   如果这种情况频繁发生，说明应该改用 §2.2 第 2 个方案，把目的地做成符号声明。
4. 自动重新打开失败后的重试次数和退避。
