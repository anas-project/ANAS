# Incus 设计简化评审

状态：评审，未改动实现。基线：`dddae0c2` 加当前工作树。只读核对了设计文档、计划与源码；文中规模数字是非测试
Go 源码的行数。每条都标了性质：观察到的现状、设计债，或待核实。

## 结论

复杂度主要来自三个前提：

1. 网络放行逐实例进行、带期限、每次都要证明实例身份；
2. 为一个还没有消费者的入站能力，提前实现了完整机制；
3. anasd 与 hostd 按「互不信任」设计跨进程交接，而 anasd 本身就是 root。

操作者已接受按租约放行，前提 1 不再成立，出站部分可以整块替换；前提 2 可以通过冻结 M11 消除。这两项合起来，
能去掉约 1.8 万行源码中的大部分，也能消掉让 M10a/M11 暂停的运行 owner 问题。

| # | 位置 | 简单路径 | 性质 | 建议 |
| --- | --- | --- | --- | --- |
| 1 | M10a 出站许可 | 租约级 Incus ACL 分级，加一条静态宿主规则 | 设计债，方向已定 | 做 |
| 2 | M11 入站 | 冻结，等出现消费者再做；届时采用租约级静态规则加路由文件 | 设计债 | 做 |
| 3 | 部署热路径上的入站排空与转发撤回 | 随 1、2 一起移除 | 观察到的现状 | 做 |
| 4 | hostd 对调用方的身份核验 | 保留动作清单、确认与审计，简化跨进程身份链 | 设计债，属于 Core | 另立评审 |
| 5 | 控制连接转发服务 | Incus 直接监听控制网桥的网关地址 | 待核实 | 先验证 |

操作者确认（2026-09-28）：

- 第 1、4、5 项同意；
- 第 2 项（入站）另开对话讨论；
- 第 3 项拆开处理：转发撤回随第 1 项一起移除；入站排空和工作区围栏等第 2 项有结论后再定。

## 1. 出站许可（M10a）

**现状。** 许可由逐实例的 nft/ipset 元素组成，期限 30 秒，另有 bridge 层来源绑定、回执与 pending 步骤、失败撤回、
显式退役和墓碑。生产启用还缺续期 owner，而 grant 又绑定在部署 epoch 上，部署之后无法续接。相关代码：

- `internal/incusingresshost/forwarding_*` 约 2,800 行；
- `internal/incusprovision/forwarding_*` 约 1,460 行；
- 另有宿主动作登记和 jobexecutor 里的撤回接线。

**简单路径。** 见[出站分级草案](2026-09-28-compute-egress-tiers-draft.md)：

- 档位写进租约网桥的 Incus network ACL。每个租约网桥已经挂着这份 ACL，Provider 也已有 `inspect`/`ensure`；
- 宿主侧在 `incus.configure` 时加一条静态规则，把租约网桥的转发交给 ACL 决定；
- 撤销时，由 Provider 在 `INCUS-R-111` 路径里把 ACL 改为全部拒绝，并停止该租约的实例。

**取舍。** 放弃逐实例的身份核验（`INCUS-R-102`）。同一租约的实例属于同一个消费者，权限本来就相同；跨租约之间
靠独立网桥和来源围栏隔离。出站方向从此不需要续期，也不需要常驻 owner。

## 2. 入站（M11）

**现状。** 设计给出的用途是「一个只跑十分钟的 CI 作业……有一个可访问的 Web 界面」（宿主供给设计 §5.1），
但没有任何 Module 声明入站：

- Forgejo runner 明确「无入站端口」；
- AI Agent 的 webhook 入口是它自己的 Docker 服务，不在 guest 里。

为这个能力已经实现的机制包括：

- 消费者请求文件，以及受信中介的校验；
- 经 hostd 的逐次观察动作，和观察范围的计划、确认与撤销；
- 逐发布的内核许可与 30 秒期限；
- 宿主路由表、永久邻居、回复来源绑定、双向 conntrack 清理；
- 中介协调器、排空屏障与跨进程工作区围栏。

相关代码约 1.3 万行：`internal/computeingressruntime` 约 7,000 行、`internal/computeingress` 约 1,200 行，
以及 `internal/incusingresshost` 的非转发部分约 5,600 行（其中少量与转发共用）。

**简单路径。** 冻结 M11，设计文档保留作为调研记录。等真正出现消费者时，按租约级信任来做：

- `allowed_ports` 已经在 apply 时冻结；
- 宿主侧放一条静态规则：Traefik 入站网络可访问租约网段的这些端口；
- 中介只负责校验请求、写 Traefik 路由文件，不再做逐发布的 root 网络动作。

逐发布许可、地址路由表、回复来源绑定和期限，在「同一租约同一信任」的前提下都不再需要。

**取舍。** 暂时失去「guest 内服务经 Traefik 发布」这项能力，而目前没有使用方。

## 3. 部署热路径

**现状。** 只要注册了工作区，anasd 就会创建入站协调器。每个工作区写任务（部署、Module 变更、凭据轮换、快照维护）
在领取之前，都要先经过协调器排空。启用宿主动作时，还会额外发起一个 `incus.forwarding.withdraw` 宿主 job，
没有任何转发记录时也照样执行（`internal/jobexecutor/workspace_ingress_change.go`、`cmd/anasd/main.go`）。
跨进程工作区围栏会让中介活跃期间的 CLI 写操作被拒绝。

**简单路径。** 1 和 2 落地后，出站策略随部署声明生效，入站也冻结了，这些领取前的协调和围栏就都可以移除。
普通部署路径恢复为只取工作区锁。

## 4. hostd 对调用方的身份核验（属于 Core）

**现状。** anasd 以 root/root 运行，没有设置能力边界，并且能访问 Docker socket，本身已等价于 root。hostd 仍然：

- 核验调用方就是真正的 `anasd.service`：`SO_PEERCRED`、固定安装策略、PID 1 私有总线报告的进程身份；
- 用固定私有 broker 做跨进程 job 交接和复核；
- 通过 D-Bus 保持 unit 引用，读取独立的退出证据（宿主通道设计 §8—§13）。

对一个已经是 root 的调用方做身份核验，构不成安全边界。

**简单路径。** 真正有价值的部分全部保留：编译进二进制的动作清单、「用户看到的就是执行的」二段确认、审计、系统写
路径与 anasd 的沙箱分开。在此基础上，把对 root 调用方的身份链简化掉。退出证据如果只用于判断 job 终态，可以改用
更轻的机制。

**取舍。** 这涉及 `HOSTACT` 需求，影响所有宿主动作，不属于 Incus 计划，建议单独评审。

## 5. 控制连接转发服务（待核实）

**现状。** 非 root 的转发服务监听控制网桥的网关地址，再把字节转发到回环上的 Incus 8443（宿主供给设计 §3.6、
§3.7）。设计否决「daemon 对外监听」的理由是它会改变默认的安全边界。

**可能的简单路径。** 让 Incus 的 `core.https_address` 直接监听同一个网关地址。暴露面与转发服务相同，仍然由 mTLS
和防火墙约束，但少一个服务、账号和它的安装与卸载流程。

**待核实。** 开机时 Incus 与 Docker 网桥的启动顺序：地址不存在时 Incus 能否正常绑定。这可能正是需要转发服务
的真实原因，需要实机验证后再决定。

## 看过但不建议改

- **M10 宿主供给**（Web 触发安装与卸载、发行版声明表）：已完成并通过验收。后续新增发行版（M14）时，可以考虑
  只在安装器里支持。
- **M12 镜像**（构建一次、摘要冻结、prune 与回滚）：可复现性是硬需求，复杂度与收益相称。
- **project 围栏与每租约一张证书**：这是多消费者隔离的核心，保留。
