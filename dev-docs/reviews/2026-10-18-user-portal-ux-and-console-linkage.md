# 用户门户设计问题、与 ANAS 控制台联动及视觉重设计

基线：2026-10-18，`0889af2e` 加当前未提交工作树。范围为
[独立用户门户设计](../../docs/architecture/user-portal-design.md)、
[门户用户管理与邮箱方案](../../docs/architecture/portal-account-mail-administration.md)、
`modules/user_portal/portal/`（Go 后端与 `ui/` 原生 JS 前端）以及 `web/`（anasd 控制台）。
只读审查，未改实现；未登录 finance 实际页面，界面结论来自源码阅读。

区分：**缺陷**＝当前调用链可复现的问题；**设计债**＝能用但会持续增加成本；**建议**＝未实现的方案。

## 1. 当前设计的问题

### 1.1 权限与安全

| # | 类型 | 问题 | 依据 |
| --- | --- | --- | --- |
| P1 | 缺陷（高；已按 PORTAL-R-074 收紧，2026-10-19 finance 实机验收通过） | 在近期认证窗口内（默认 5 分钟），把人加入 `Admins` 只需一次点击，没有页内确认，也不要求本人域密码。`Admins` 是 `platform_admin`；anasd 启用 `trusted_proxy` 时该组映射为控制台 `owner`，可控制 Docker、恢复数据、读取凭据，权力高于 Domain Admins 之外的任何门户动作，却按“普通受管组添加”处理 | `administration.go:83-87` 只有 `DomainRisk` 才要求域验证，`directory_admin.go:85-86` 中 Admins 组 `AdminRole=true` 但不是 `DomainRisk`；`app.js:385` 中 `needsConfirmation=!add||!managed||requires_domain` |
| P2 | 设计债 | 一个组同时表示“应用最高管理员”“门户全员管理”“控制台宿主 owner”三层含义。想让 helpdesk 管人，就只能给他宿主控制权，或退回配置文件里的委派规则 | `admin-account-system.md` §2 已警告；`trusted_proxy.platform_admin_group` |
| P3 | 设计债 | 门户里管人有两条授权路径（平台角色 + `delegation_rules` JSON），后者只能改配置并重新部署，界面上看不到规则来源 | `user-portal-design.md` §2.2 |

### 1.2 信息架构

| # | 类型 | 问题 |
| --- | --- | --- |
| P4 | 设计债 | “管人”的入口有四个：门户用户管理、LAM（`kind: admin`）、Casdoor 后台、Samba 命令行。没有一处说明“日常用门户，LAM/Casdoor 只用于恢复” |
| P5 | 缺陷 | ANAS 控制台本身不在应用目录里（anasd 不是 Module），门户“后台管理”组看不到最重要的那个后台 |
| P6 | 缺陷 | 前端没有路由：页面状态只在内存变量 `page/target`，刷新回到首页，浏览器后退离开门户，无法给出“打开某个用户”的链接，控制台也就无法深链过来 | `app.js` 无 `location.hash`/`pushState` |
| P7 | 设计债 | “我的账号”“修改密码”“安全记录”是三个平级导航，其实都属于个人设置；“用户管理”与个人功能挤在同一侧栏，普通用户与管理员视角没有分开 |
| P8 | 设计债 | 每次切换页面都重新请求 `/api/me` 并清空内容区，切页有闪烁的“加载中” | `app.js:100-106` |

### 1.3 视觉与交互

| # | 问题 |
| --- | --- |
| V1 | 首页是“标题 + 搜索框 + 下拉 + 复选框 + 卡片网格”，与一般后台列表页无异；没有个人化问候、常用/最近、账号状态提醒等“门户”应有的第一屏 |
| V2 | 应用卡片 48px 图标 + 两行灰字 + 一个文字链接“打开应用” + 折叠“详情”。点击区域只有那行文字，卡片本身不可点；“详情”展开会撑乱网格高度 |

| V7 | 语言切换下拉常驻页头；退出按钮与语言并排，没有头像/账号菜单 |

## 2. 门户与 ANAS 控制台的联动方案

### 2.1 分工原则

| 系统 | 管什么 | 不管什么 |
| --- | --- | --- |
| 用户门户 `portal.*` | **人与应用**：应用入口、个人账号、人员/分组、身份安全记录 | Module、部署、备份、宿主 |
| ANAS 控制台 `anasd` | **系统与服务**：workspace、配置、部署、生命周期、Module、网络、维护、任务、系统审计 | 用户与分组数据（只读引用身份） |

两站共用 Casdoor SSO，不共享会话、不互相调用写 API。门户不持有控制台凭据；控制台不复刻用户管理界面。

### 2.2 具体联动点（按优先级）

1. **拆分宿主权限（修 P1/P2，先做）**
   - 短期：门户把 `AdminRole` 组的加入与移除都按域级风险处理，必须页内确认、近期认证和本人域密码；后端 `operationTarget` 与 `adminGroups` 同步修改，不只改前端。
   - 中期：新增独立的“宿主管理员”组（例如 `ANAS Host Admins`，经 identity Provider 注册），`trusted_proxy.platform_admin_group` 指向它；`Admins` 回到“应用最高管理员 + 门户全员管理”。门户把宿主管理员组列为受保护组，只能在控制台或命令行变更。
   - 需新增需求 ID，并同步 `admin-account-system.md`、控制台配置参考。
2. **门户前端加 hash 路由（修 P6，联动前提）**：`#/apps`、`#/me`、`#/me/security`、`#/admin/users`、`#/admin/users/<anchor>`、`#/admin/groups/<anchor>`。与控制台 `nav.ts` 相同做法，不需要改服务端路由。
3. **控制台进入应用目录（修 P5）**：启用 `trusted_proxy` 时，Core 生成一条 `kind: admin`、`categories: [system]`、`access: forward_auth + role: platform_admin`（中期改为宿主管理员组）的目录条目，与 Module 条目走同一 `BuildView`。门户“后台管理”第一项即为 ANAS 控制台。
4. **双向深链**：
   - 控制台 → 门户：页头“用户与分组”链接到门户 `#/admin/users`；系统审计中出现人员 anchor 时链接到门户该用户页；Module 页的“打开应用”链接复用目录 URL。
   - 门户 → 控制台：后台管理卡片打开控制台；用户详情中“该用户可访问的应用”旁可跳到控制台对应 Module 页（`#/modules?name=`，需控制台小改）。
5. **维护状态只读广播（可选）**：Core 在部署/维护任务开始和结束时，向已有的共享清单目录写一个 `status.json`（Module 名 → `ok/maintenance/degraded`），门户只读挂载，在对应应用卡片上显示“维护中”。复用 `identity-groups/catalog.json` 的挂载方式，不新增服务或 API。
6. **统一入口说明（修 P4）**：门户“后台管理”分类给 LAM、Casdoor 标注“恢复/高级”，并在其简介中写明日常管人用门户；不移除它们。
7. **共享设计变量（修 V3）**：新增一份 `tokens.css`（颜色、字号、间距、圆角、阴影，含暗色），门户与控制台各自构建时复制同一文件；不引入共享组件库。

### 2.3 复杂度

整体 **低—中**。第 1 项改后端授权判断和一个配置字段，第 2、4 项是前端改动，第 3、5 项复用现有目录与共享文件机制；没有新服务、新数据库或跨站 API。中期拆组涉及 Provider 组注册、迁移现有 `Admins` 成员是否同时进入新组，需要用户确认迁移策略。

## 3. 视觉重设计（不受现有实现约束）

原型见同日发布的 HTML 设计稿（链接记录在答复中，不入库）。要点：

- **两种模式**：普通“工作台”（应用 + 我的账号）与“管理”模式；管理员在页头切换，管理模式改用深色侧栏，避免误操作。
- **首页即启动台**：按时段问候；账号提醒条（密码将过期、需要改密）；`⌘K` 全局搜索应用与（管理员）人员；“常用”行 + 分类应用网格，卡片整块可点，悬停显示简介与文档入口。
- **账号页做成设置页**：左侧二级导航（资料、密码与安全、分组与权限、邮箱、安全记录），每个区块一张卡片。
- **管理用户详情**：上方身份卡（头像、状态徽章、管理员标记），下方标签页；危险操作集中在“危险区域”，红色边框，需确认。
- **结果状态**：写操作结果用三段步骤条显示“目录已保存 → IAM 同步 → 应用会话”，每段独立状态。
- **设计体系**：中性石墨灰 + 一种靛青主色，系统字体栈（中文 PingFang/思源黑体），4px 间距基准，12/14/16/20/28/40 字号，明暗两套变量。

## 4. 建议的下一步

1. 用户确认 P1 的处理（短期按域级风险）与中期拆组方向，补需求 ID。
2. 门户 hash 路由与目录中的控制台条目，可与 P1 并行。
3. 视觉重设计确认后，先落地设计变量与首页，再迁移账号页和管理页。
