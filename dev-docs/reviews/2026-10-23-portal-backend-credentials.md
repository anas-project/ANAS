# 门户后台账号复制与 anasd 服务授权方案

调查基线：`058d5c2ce872` 加 2026-10-23 当时工作树。以下保留实施前的调查与方案比较，
不是当前操作说明或验收报告；调查未部署、未验证真实后台登录，也未读取实际凭据。
同日用户确认实施方向 A：现有 5 分钟本人认证、每服务令牌、anasd 自动续期与启动交付。
已采纳要求进入[需求矩阵](../requirements/service-api.md)，实现与验证结果只在
[配套计划](../plans/archived/service-api.md)更新；当前配置和接口见[服务 API](../../docs/architecture/service-api.md)。
下文“建议”“尚未实现”是调查时点的历史状态。

## 1. 用户目标与交互草案

用户要求：门户内没有接入 IAM 的后台管理功能，应允许管理员直接复制用户名和密码，
获取时可以实时验证用户密码。

用户确认：**验证当前登录门户管理员本人的密码，沿用现有 5 分钟近期认证流程**。
有效期内复用认证结果，过期才弹框输入本人密码；不尝试登录目标后台验证目标密码。

候选交互：后台卡片提供“获取登录信息”入口 → 门户检查当前身份、管理员权限和近期
认证 → 必要时页内验证本人密码 → 通过服务 API 读取对应后台地址、用户名和密码，
分别提供复制按钮。每次请求仍检查当前权限；5 分钟有效期不缓存用户权限或目标凭据。
关闭弹框清除页面内结果；密码不进入应用目录、偏好、URL 或日志。

## 2. 已核实的入口与凭据

| 入口 | 当前实际登录与凭据来源 | 本功能的候选处理 |
| --- | --- | --- |
| Traefik | `management.local_accounts.primary`，Secret Store 保存密码，应用使用 bcrypt | 绑定此本地管理账号 |
| DDNS-Go | `management.local_accounts.primary`，Secret Store 保存密码，应用使用 bcrypt | 绑定此本地管理账号 |
| Collabora | `COLLABORA_ADMIN_USERNAME` 与 `COLLABORA_ADMIN_PASSWORD`；尚未声明 `local_accounts` | 显式登记现有后台凭据来源，不自动迁移或重置账号 |
| LAM | 主登录使用本人 AD 账号；`LAM_ADMIN_PASSWORD` 仅保护配置页面，无对应用户名 | 不把配置密码冒充目录登录密码；是否新增独立配置入口另行确认 |
| DDNS Updater | Compose 通过 ForwardAuth 接入 IAM，无自有用户名密码；目录仍标 `local` | 不提供复制；不能仅凭目录的 `local` 标记判断 |
| Casdoor | 日常管理接入 IAM；`break_glass` 是应急恢复账号，地址不同 | 不因存在本地恢复账号而自动开放复制 |
| Forgejo / Nextcloud | IAM 应用卡片，另外存在应急恢复账号 | 不自动开放恢复账号 |
| PostgreSQL / MariaDB 的 Adminer | 入口通过 ForwardAuth；数据库登录凭据是另一层权限 | 不自动交付数据库 root 密码 |

依据：各 Module 的 `module.yml`、`docker-compose.yml`，以及
[LAM 说明](../../modules/lam/README.md)、[DDNS Updater 说明](../../modules/ddns_updater/README.md)。
应用必须显式绑定用途正确的凭据，不能按名称、`kind: admin` 或是否存在密码推断。

## 3. 可以复用的代码与缺口

- [门户密码核验](../../modules/user_portal/portal/reauth_password.go) 已有本人 LDAPS 验证、
  当前人员/GUID 校验、限流和审计。按用户确认复用 `recentSession()` 的 5 分钟结果；
  权限与人员状态仍逐次检查，不能因近期认证有效而略过授权。
- [门户界面](../../modules/user_portal/portal/ui/app.js) 已有 `applicationCard()`、
  `appInfo()` 和 `copyButton()`；应用列表只需返回可获取标志，不返回秘密。
- [共享维护服务](../../internal/runner/maintenance_application.go) 的 `RevealLocalAdmin()`
  从 Secret Store 读取当前值；[控制台接口](../../internal/api/httpapi/maintenance_routes.go)
  已有一次性目标绑定核验、审计与 `no-store`。
- 门户没有调用上述服务的现成通道。[控制台代理认证](../../internal/api/httpapi/auth_routes.go)
  不接受密码核验请求，不能直接把门户密码传入现有 step-up 接口。
- [现有密码文件](../../internal/runner/local_admin.go) 只为 `plaintext_on_bootstrap`
  账号生成；Traefik/DDNS-Go 不在此范围。门户降权为 UID/GID 65532，不能直接读取
  现有 0600 密码文件。[轮换](../../internal/runner/admin_cli.go) 包含这些文件的提交与恢复。

## 4. 交付方案比较与当前方向

| 方案 | 实现范围 | 收益 | 成本与复杂度 |
| --- | --- | --- | --- |
| A：通过现有 anasd 按需读取 | 门户增加专用获取接口；anasd 增加仅限明确后台凭据的服务间授权入口，复用现有 Secret Store 读取；Collabora 补显式来源 | 无新增密码副本，轮换后读取权威源 | **高**：新增信任边界、受限授权、部署连接配置和不可用处理；复制功能新增 anasd 运行依赖，但不新增独立进程 |
| B：专用只读凭据文件 | Core 从权威源生成门户专用文件，只含明确登记的后台凭据；门户只读挂载；扩展 apply、轮换、恢复和撤销处理 | 无新增服务依赖，复用现有文件交付机制 | **中**：新增敏感副本及访问权限，需要覆盖轮换/恢复失败，防止旧密码继续可取；不是简单写一个 JSON 文件 |

用户当前方向为 A，并将其明确为可供其他服务共用的 anasd 服务授权与 API，职责见下一节。
B 保留为此前比较的简单部署替代项。尚未选定具体服务凭据协议，不将候选通道描述为现有能力。
把完整 Secret Store 挂入门户、把密码加进 `catalog.json` 均不属于候选方案：它们扩大
读取范围，也不符合现有应用目录与目录绑定凭据的边界。

设计确认依据：[AGENTS.md](../../AGENTS.md) 要求高复杂度设计实施前取得确认，
并明确将“keeping data in multiple places synchronized”列为需要说明和确认的复杂度示例。
当前已完成源码调查与职责方向确认，功能代码尚未修改。

## 5. 服务调用机制：用户确定的职责与最小实现建议

### 5.1 职责

| 层 | 负责什么 |
| --- | --- |
| 浏览器 | 向门户发起用户操作，接收门户返回的结果 |
| 门户 server | 验证用户会话、当前身份/角色、对象可见性、CSRF 和 5 分钟近期认证；决定用户能否发起请求 |
| anasd | 验证调用服务身份，检查已授予该服务的 API 权限和工作区/对象范围，执行 API 自身的数据与状态约束，记录审计 |

anasd 信任已授权服务在授予范围内作出的用户授权决定，不重复登录目录或接收用户密码。
服务可以附上用户 anchor 和请求 ID 供审计关联；该用户信息是调用方报告的上下文，
不能替代服务身份或扩大授权。anasd 的操作主体是服务，终端用户是单独记录的发起人。
最终可交付范围是“调用服务授予范围”与“该服务允许用户操作的范围”的交集。

### 5.2 最小机制建议（尚未实现）

1. 每个服务实例注册独立客户端身份，例如 `user-portal-main`，按部署分别授权。
   anasd 管理客户端的启用/停用、凭据签发/替换和撤销，服务不能给自己加权。
2. 初版建议 HTTPS 加每客户端独立的高熵随机令牌。anasd 保存令牌摘要，调用方通过
   私有文件取得原值；服务凭据不进入浏览器。替换和撤销要有明确的生效边界，不能
   依靠启动时读取一次的配置而宣称立即撤销。具体管理命令和交付方式在实施设计中确定。
3. 复用 [RoutePolicy](../../internal/api/httpapi/security.go) 的 `Permission` 和
   `Scope`，显式声明允许服务调用的路由。授权同时约束 API 动作与工作区、应用等
   对象范围；不采用任意 URL 前缀放行，也不把服务身份映射成控制台 `owner`。
   每条授权将动作与对应资源范围一起保存，避免多个动作和多个资源被错误组合放行。
4. 例如门户取得 `application.credentials.read`，并只限指定 workspace 内明确登记的
   后台应用。此名称是建议的权限标识；没有授予的 API 或对象默认拒绝。后续服务使用
   同一认证与授权入口，按具体需要增加权限和业务 API。
5. 凭据读取使用专门的服务 API，复用 [共享维护服务](../../internal/runner/maintenance_application.go)
   中的读取逻辑。现有控制台 reveal 保留其用户 step-up 规则，不在通用服务入口中
   放宽控制台会话检查。普通数据查询可复用同一应用服务，按路由显式适配。
6. 服务授权配置由 anasd 宿主管理员控制，持久状态位于 workspace 外的控制面存储。
   workspace 配置、快照恢复和调用服务自身的请求不能新增或恢复宿主授权。

现有实现已有路由权限、对象参数、工作区 Registry 和应用服务；新增的是服务身份、
授权记录、凭据管理和服务 API 适配。现有 `trusted_proxy` 是 Traefik 的用户身份通道，
包含用户 Cookie、CSRF 和 owner 映射；不能直接当作通用服务授权。

整体复杂度仍为**高**，主要来自跨服务信任、客户端凭据生命周期、按对象授权和部署接线。
共用认证与授权代码能减少后续服务的重复工作；首个接入只实现门户所需的业务 API。
不预先开放配置写入、部署、任意命令等与当前数据请求无关的能力。

## 6. 后续验证建议

确认范围后，将适用条件写入需求矩阵、执行结果写入配套计划。建议覆盖：普通用户与
撤权拒绝、错误密码、停用/锁定、5 分钟认证复用与过期、IAM/隐藏/不可见入口拒绝、
CSRF、限流、审计失败、轮换后当前值、读取失败，以及秘密不进入目录/日志/偏好和弹框清理/复制回退。
服务层另验证错误/撤销令牌、跨工作区与跨对象、未授权 API、服务身份冒充 owner、
调用方报告的用户上下文不扩大权限，以及 workspace 恢复不恢复已撤销的服务授权。
实机部署和浏览器验证尚未执行，源码调查不代表验收通过。
