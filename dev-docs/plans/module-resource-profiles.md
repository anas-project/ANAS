# Module 资源运行方式实施计划

**目标版本：下一版本，未指定具体发布号。** 本计划覆盖所有 Module，不作为本版 Immich 接入的阻塞项。
验收依据为 [同名要求](../requirements/module-resource-profiles.md) 的需求矩阵；
机制见 [架构设计](../../docs/architecture/module-resource-profiles.md)。

## 1. 落地快照

2026-10-02：本次只有文档，没有新增运行档 schema、自动内存检测、调度器或 Module 行为。
既有配置类型/默认值、条件 capability、可选服务、配置变更分类、锁和 deployment 是复用入口，
不将它们的存在等同于本计划已经实现。

当前 Immich 接入按独立 [设计](../../docs/architecture/immich-module-design.md) 推进：
专属 Redis、OIDC-only、共享 PostgreSQL 和现有备份。无需先交付本主题。

### M0：声明边界

验收入口：要求 §1—2。先从 inventory 盘点默认方式、可选服务、已有并发参数和无法降级的模块。
基于现有 manifest/config 加入最小可选声明，确定未知值和配置优先级；不要先设计独立插件协议或资源服务。
旧 Module 不修改也能保持原行为；新增默认声明不等于新增可用运行档。

### M1：资源证据与预算

验收入口：要求 §3。复用已有目标/运行时观察，补齐实际目标的内存与限制读取；先实现确定性只读计算。
加入主机保留量、已有工作区预算、共享实例去重与峰值负载规则。
提供未知/不足的反例，验证同一输入不会因调用顺序产生不同推荐。
不要通过观察此刻空闲内存来悄悄覆盖已选配置。

### M2：现有生命周期接线

验收入口：要求 §4。将有效配置送回既有依赖解析与冻结流程；在现有 CLI/Web 计划视图展示差异。
使用现有变更分类和 apply 入口，覆盖计划过期、并发变更、失败补偿及历史 deployment 回滚。
资源限额按实际 runtime 能力落地；只有声明/渲染、没有执行效果的场景不能显示成已强制限制。
远程计算、临时目录切换和共享 Provider 的能力冲突各走现有对应边界，不附带扩张职责。

### M3：分批覆盖全部 Module

验收入口：要求 §1、§3 与矩阵的覆盖/容量条目。
先选择具有不同特征的代表：Immich 的 ML/媒体处理、共享 PostgreSQL、一个轻量服务以及一个已有可选服务的 Module。
这些是首批验证对象，不是支持清单的终点；每批从 inventory 派生遗漏项直到所有模块被明确分类。

每个 Module 交付以下之一：经验证的多种方式；经验证的单一默认方式；尚未验证的明确记录。
只有前两类可以宣称已完成该模块适配；“不适用多档”也要说明保留行为及依据。
新增 Module 的门禁要求同步分类，不让清单随仓库增长再次失效。

4GB/8GB 及“宿主较大、运行环境限额较小”是候选实验维度，不是预先承诺的普适阈值。
记录启用模块全集、共享依赖、版本、媒体/任务规模、并发、峰值、OOM、延迟和功能结果。
图库场景覆盖首批导入、持续手机上传、视频、索引与备份重叠；不能只测试缩略图全生成后的空闲状态。
