## 3. 实施顺序与检查表

先做 M4 的目标镜像小型试验，为 M0 声明提供实际约束；再完成 M0 和 M2 的分配/删除安全检查，随后接入 M1。M2 的查看命令可在这些检查稳定后完成。M3 恢复回归与 M4 完整编辑验收在首版交付前完成。

- [ ] **M4 前置试验：**验证固定 Collabora 镜像的 child-roots 外部挂载、模板同文件系统、UID/GID 与启动清理行为，据此选择最小可行布局。若单目录挂载不足，先记录具体限制及所需初始化范围，避免先冻结一个不能承载目标镜像的声明格式。验收入口：需求 §2、R-030。
- [ ] **M0：**补齐 `global.temp_path` 的 schema、配置 effect 与路径解析；定义 Module 临时目录声明及宿主目录分配，接入环境/挂载生成。配置是可选显式声明，不扫描和接管未声明目录。验收：需求 §1—§2。
- [ ] **M0：**复用 workspace 锁、路径与所有权检查，落盘容器目录登记；区分已持锁的内部调用和顶层命令，避免重复获取同一锁。覆盖 CLI/管理服务停启与目录分配、回收的互斥。验收：需求 §2、§3.1，R-012、R-043。
- [ ] **M2 安全检查：**先完成目录释放核验、异常对账与空间预检，供分配、M1 旧目录清理和显式 GC 共用；不要在 M1 内另写一套删除逻辑。验收：需求 §5。
- [ ] **M1：**在已有排他锁内接入目标预检与 deployment 准备，串联旧 Module 停止、新目录分配与容器重建、实际挂载核验、状态提交及旧目录回收；保留旧/新 deployment 各自的 Module 集合与依赖顺序。验收：需求 §3。
- [ ] **M1：**接入现有失败补偿和阶段记录；补齐预检失败、停止失败、新实例启动/挂载失败、状态提交中断及清理失败重试的反例。应用仍在初始化的场景按 R-044 验证，不新增通用健康等待或保存确认流程。验收：需求 §3.1—§3.2。
- [ ] **M1：**让历史回滚复用同一个临时路径比较和切换入口，依据历史配置生成新的目标 deployment；覆盖相同路径、目标旧盘缺失和历史目录已清理。验收：需求 §4、R-041。
- [ ] **M2 查看与 GC：**实现拟新增的 `anas temp status`、`anas temp gc --dry-run` 和 `anas temp gc`（当前不可执行），输出当前/历史根中的 Module 目录状态及回收阻碍。运行问题展示可接已有机制，空间预检独立可用。验收：需求 §5。
- [ ] **M3：**验证备份四种传输模式及快照覆盖；在备份恢复、快照恢复与克隆后的启动路径接入目标身份、目录重新分配及运行挂载。核对不可变制品中的源路径不会绕过分配入口。验收：需求 §4。
- [ ] **M4 接入与验收：**提交 Collabora 声明及相应挂载/镜像配置，通过真实打开、编辑、保存、关闭、再重开，以及正常停止和重建后的数据往返；应用停机保存异常归 Module 修复，测试成功不转换成每次切换的 Core 保存协议。验收：R-029—R-030。

## 5. 阻塞与待决策事项

- Collabora 单独绑定 child-roots 的兼容性尚未验证，是 M4 上线阻塞；试验先于 M0 声明定稿，不能由单元测试推断真实编辑验收。
- 外部文件系统身份跨重启的稳定表达、首次登记时是否位于预期磁盘的证明，以及安全拒绝目录集合需在 M0 定稿。
- 已有 workspace 身份是否能复用、克隆后如何重新签发身份需在 M0 定稿；不能仅用绝对路径哈希标识 workspace。
- Docker init 候选方案：同时持久保存客户端程序的绝对路径与实际本地连接地址，后续由 Runner 读取并显式用于子进程；仅固定程序或设置 init 进程环境不能固定后续命令连接。该方案尚未批准改变 CLI 的默认 context 行为，不进本次矩阵。若采用，先协调 Compose 执行边界和 anasd workspace 注册，再明确记录位置、初始化尚无 Docker 的处理、连接更新及恢复后重新绑定。当前阶段复用现有命令上下文，查询失败或引用无法确认时不清理。
- 应用全面就绪、Core 保存确认、Runner job 排空、失败 job 保留与远程测试产物不再列作本功能的交付阻塞。
